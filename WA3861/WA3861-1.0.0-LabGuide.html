Evergreen Insurance Quote API: Building a Server with Node and Express

Lab 1

In this lab, you will build the first back end for Evergreen Insurance: a small Node.js + Express server that serves the quote data over HTTP. Until now, everything lived in the browser. After this lab, the quotes come from a real API, the same kind your engineers build and the React app would call.

This is Week 2 of Phase 3. Last week you directed an AI assistant through JavaScript changes and verified them with tests; this week you build the kind of server that work targets.

You are not expected to become a back-end developer. You are here to see what an API actually is: a set of URLs ("routes") that return data, built from a handful of clear, repeatable pieces.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

"The endpoint returns a 404," "add a route for that," "the POST body isn’t parsed": these are everyday API review comments. After building four routes yourself, each one becomes concrete. You will also see the clean split between front end (the React app) and back end (this server) that organizes nearly every system at Liberty Mutual.

1.3. What’s Already Set Up on Your Lab VM

  • The starter project: a package.json, the quote data and premium math in src/quotes.js, and src/index.js with a running server shell and TODO route handlers.

1.4. Open the Project and Run It

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-express-api in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-express-api.

  4. In that same terminal, install the dependencies and start the server in watch mode:

    npm install
npm run dev

    You should see Evergreen Quote API running on http://localhost:3000.

     Note

    npm run dev runs the server with node --watch, which restarts it automatically every time you save a file: the back-end cousin of the instant reload you saw in the Phase 2 React labs (many teams use a tool called nodemon for the same job). If you used npm start instead, you would have to stop the server (Ctrl+C) and start it again after every change.

  5. Open http://localhost:3000 in Chrome. You see a JSON status message. Your server is live.

    Figure 1. The health check: the server answers with JSON before you have written a single route

 Note

Leave the server running in this terminal for the whole lab; watch mode restarts it on every save. For the curl commands you are about to run, open a second terminal beside it: Terminal → Split Terminal (or Ctrl+Shift+5).

1.5. The API at a Glance

You will fill in four TODO`s in `src/index.js, each one a small, complete idea:

  1. List all quotes (GET /api/quotes): the simplest possible route, a URL that returns the whole list.

  2. One quote by id (GET /api/quotes/:id): a route parameter, and your first deliberate 404.

  3. Create a quote (POST /api/quote): read a request body, validate it, calculate a premium, return 201.

  4. Catch everything else (a 404 handler): a safety net placed after all the routes, because order matters.

Think of the server as a small claims office: each route is a service window that handles one kind of request, and the 404 handler is the greeter at the door who politely turns away anyone who wandered into the wrong building.

 Tip

Every snippet below replaces a numbered TODO comment in src/index.js. The TODO comments themselves describe what each route must do, so if you lose your place, the file tells you which move you are on. After each save, watch the first terminal: the watch process prints the startup line again, which is how you know the new route is actually loaded.

1.6. Understand the Basics

  1. Open src/index.js. Notice three things every Express app has:

    • const app = express(); creates the application.

    • app.use(express.json()); registers middleware that parses JSON request bodies so req.body works.

    • app.listen(PORT, …​) starts the server listening for requests.

Why this matters: Every Express server, no matter how large, is this same skeleton plus routes. You are about to add the routes.

1.7. List All Quotes (GET)

  1. Replace TODO 1 with a route that returns the list:

    app.get("/api/quotes", (req, res) => {
  res.json(quotes);
});

  2. Save. In the first terminal, the watch process restarts the server; the startup line prints again.

  3. In the second terminal:

    curl http://localhost:3000/api/quotes

    You get back the JSON array of four quotes, q1 through q4, starting with {"id":"q1","type":"auto",…​}.

    Figure 2. Two terminals: the server runs on the left while curl talks to it from the right

Why this matters: app.get(path, handler) is the core of an API: when a request comes in for this URL, run this function and send a response. res.json(…​) serializes data to JSON and sets the right headers.

1.8. One Quote by ID (Route Parameter)

  1. Replace TODO 2:

    app.get("/api/quotes/:id", (req, res) => {
  const quote = quotes.find((q) => q.id === req.params.id);
  if (!quote) {
    return res.status(404).json({ error: "Not found" });
  }
  res.json(quote);
});

  2. Save and test both the found and not-found cases:

    curl http://localhost:3000/api/quotes/q1
curl http://localhost:3000/api/quotes/nope

    The first returns {"id":"q1","type":"auto","age":41,"coverageAmount":50000,"monthlyPremium":96}; the second returns {"error":"Not found"} with a 404 status.

Why this matters: :id is a route parameter, a placeholder filled from the URL and read via req.params.id. And res.status(404) is how an API says "I looked, it isn’t here." Correct status codes are what let the front end react properly.

1.9. Create a Quote (POST with a Body)

  1. Replace TODO 3:

    app.post("/api/quote", (req, res) => {
  const { type, age, coverageAmount } = req.body;
  if (!type || age === undefined || coverageAmount === undefined) {
    return res.status(400).json({ error: "type, age, coverageAmount required" });
  }
  const monthlyPremium = calculatePremium(type, Number(age), Number(coverageAmount));
  const newQuote = {
    id: randomUUID(),
    type,
    age: Number(age),
    coverageAmount: Number(coverageAmount),
    monthlyPremium,
  };
  quotes.push(newQuote);
  res.status(201).json(newQuote);
});

  2. Save and test:

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"auto","age":35,"coverageAmount":50000}'

    You get back the new quote with status 201 Created: a fresh generated id and, for these inputs, a calculated "monthlyPremium":400.

    Figure 3. The API validates the body, calculates the premium, and answers 201 Created

  3. Now send a bad request and watch the validation:

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"auto"}'

    You get {"error":"type, age, coverageAmount required"} with status 400.

Why this matters: A POST request carries a body, parsed by the express.json() middleware into req.body. Validating it and returning 400 for bad input is the server-side guard, the back-end echo of the validation you wrote on the front end in Phase 2.

1.10. Handle Unknown Routes (404)

  1. Replace TODO 4, and make sure it sits after all the other routes:

    app.use((req, res) => {
  res.status(404).json({ error: "Not found" });
});

  2. Save and test an unknown path:

    curl http://localhost:3000/api/does-not-exist

    You get a clean {"error":"Not found"} instead of Express’s default HTML error.

Why this matters: Order matters in Express: routes are checked top to bottom, and this catch-all only works last. When an engineer says "the 404 handler has to go at the bottom," this is exactly what they mean.

1.11. Review

In this lab you:

  • Stood up a Node.js + Express server from a package.json and npm run dev.

  • Added GET routes that return JSON, including one with a route parameter.

  • Added a POST route that reads a request body, validates it, and returns 201.

  • Used proper status codes (200, 201, 400, 404) so clients know what happened.

  • Placed a catch-all 404 after the routes, learning why order matters.

You built the back end that the Evergreen front end talks to, and you now understand, firsthand, what an API really is and why review comments about routes, bodies, and status codes come up so often. Next week you will put a GraphQL view in front of this very same data and compare the two styles.
