Final Review and Capstone Project for Leaders

Final Capstone: Lead & Assemble the Evergreen Quote Launch

Lab 1

This is the last week of the whole program. For three phases you have followed Evergreen Insurance Quote: a static landing page in Phase 1, a typed React app in Phase 2, an Express + MongoDB API in Phase 3. The page estimates; the service remembers; they have never spoken to each other. This week you spend four days as the Delivery Lead for the Evergreen Quote launch: you start from a starter monorepo in your lab kit (landing/ + client/ + api/, all three parts running from minute one, deliberately unwired) and, over the week, assemble the launch: wire the React client to the API through the dev proxy, retire the stub data, align the rates, containerize the API, demonstrate the full stack on a local Kubernetes cluster, and merge it all to main with a green two-job CI run. On Friday the program ends the way programs should: with a showcase.

You will not write code from scratch. Every coding step in this capstone is an assembly step: push the starter to your own repo, branch, copy a provided piece into place, paste the kit’s two lines at a marker, configure a value, apply a provided one-line fix, run a documented command sequence, observe the result, open a PR. The skill being practiced is leading delivery, not authoring software.

Writing code is never required to complete this capstone. But if you want to get hands-on, four clearly marked optional challenges are waiting: tinting the landing page through one theme variable (Phase 1 muscle), adding renters coverage end to end across two languages and two validation systems (the flagship), scaling a Kubernetes deployment and watching it heal, and critiquing a Copilot-drafted compose file. They are entirely optional; skipping them costs you nothing and does not affect completion.

One more block is different in kind: a gated cloud extension, the Thursday-afternoon cloud window, where the launch image takes one verified pass over the real Amazon EKS, on the same sandbox AWS account you used in the orchestration week, and comes back down the same day. You do not opt into that one; the instructor opens or keeps the gate, based on the time the week has in hand, and announces the call at Thursday’s check-in. Friday’s demo never depends on it.

On Friday afternoon, it’s time for the Program Showcase: five minutes per learner or pair, presenting what three phases built and what this week shipped.

 Tip

This capstone is the culmination of every topic in the program: the Phase 1 web foundations and Git working method, the Phase 2 React + TypeScript delivery, and the Phase 3 API, database, container, Kubernetes, and AI-oversight work. A journey document in your kit, EVERGREEN-JOURNEY.md, maps all of it; you read it Monday, and each day closes with one journey-check question tying the day back to a phase.

1.1. Who You Are This Week

You are the Delivery Lead for the Evergreen Quote launch. You begin with a starter monorepo in your lab kit that represents the work of the engineering organization’s three teams: the marketing site team (landing/), the front-end team (client/), and the platform services team (api/). You are not managing a roomful of peers. You are leading a launch, and getting hands-on by assembling the provided pieces into one wired, containerized, demonstrated product, not by writing code from scratch. Expect to put pieces together as well as lead.

  • You may work solo or paired (team of two). Choose by 11:30 Monday.

  • The instructor plays the project sponsor, Priya Ramanathan; bring questions to her when a real Delivery Lead would. She also authors the week’s injects.

  • The cohort runs team meetings (daily check-in, planning, delivery review, lessons-learned review) together, with a different learner leading each day.

  • When something breaks, you route the problem to the team that owns it; you do not fix it yourself. The one-paragraph routing message is a deliverable skill this week.

 Note

"Assembly, not authoring." If you ever feel you need to write a component, a route, a manifest, or a workflow, stop: the piece you need is already in your lab kit under files/, and the kit README.md has the exact command or snippet.

1.6.2. Morning Block: Assemble (The Wiring Sequence)

  1. Open the kit’s wiring pieces.

    ls ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client

    Five files, and each one has a job:

    • vite.config.ts: adds a proxy that forwards every /api request from the dev server (and from npm run preview) to the API on port 3000. The client keeps using relative URLs; no cross-origin configuration anywhere.

    • types.ts: the app’s Quote contract with one change: id is a string now, because the API’s database assigns ids (q1 for seeded quotes, UUIDs for new ones). Numbers made up by the browser are retired.

    • api.ts: a new file, the seam itself. It declares what the API actually sends over the wire (ApiQuote, whose documents carry _id), maps wire documents to app Quote values, and exports fetchQuotes() and saveQuote().

    • QuotesContext.tsx: version 3 of the provider. The data now comes from the API and saving persists to the database, but the exported hook API is unchanged, so no component is edited. The same behavior-preserving replacement you watched in Phase 2, now at full-stack scale.

    • QuoteForm.tsx: one change from the Phase 2 version: saving no longer invents an id and a premium in the browser. The form sends only the visitor’s inputs (type, age, coverageAmount); the API assigns the id and computes the premium of record. Keep that in mind; it is about to make something visible.

  2. Copy all five into place. From the repo root, in order (these are the kit README.md "Day 2: wiring the client to the API" commands):

    cp ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client/vite.config.ts client/vite.config.ts
cp ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client/types.ts client/src/types.ts
cp ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client/api.ts client/src/api.ts
cp ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client/QuotesContext.tsx client/src/context/QuotesContext.tsx
cp ~/Labfiles/wa3870-cap-final-review-and-capstone-project-leaders/api-client/QuoteForm.tsx client/src/components/QuoteForm.tsx

  3. Retire the stub data. The old provider read a bundled JSON file, and an older version before that read a sample module. The API is the source of truth now, so both stubs leave the repo, through Git, on the record. This is a decommissioning: a system that served for two phases is being turned off because something better is live, and the deletion goes in the diff like everything else:

    git rm client/src/sampleQuotes.ts client/public/quotes.json

  4. Restart the client dev server. Stop it with Ctrl+C and start it again with npm run dev (the proxy in the new vite.config.ts loads at startup). Make sure the API dev server from yesterday is still running in its own terminal; the proxy needs something to forward to.

  5. Ask the compiler whether the seam holds. Five files changed hands this morning. Before trusting your eyes, check the contracts:

    cd client
npm run type-check

    It reports exactly one error:

    src/api.ts(27,13): error TS2339: Property 'id' does not exist on type 'ApiQuote'.

    Read what happened. The mapper in api.ts reads doc.id, but the wire contract says API documents carry _id; the compiler read the contract across the seam no human in this program ever crossed, and refused. The dev server would have run this code without complaint; the bug would have surfaced as quotes with a missing id, at some later, worse moment. This is the same gate that caught the Phase 2 QA bug, now standing between two systems instead of two files.

  6. Apply the kit’s one-line fix. The kit README.md ("Day 2: the one-line seam fix") shows the exact before and after: in client/src/api.ts, find id: doc.id, and replace it with id: doc._id,. Run npm run type-check again: clean. Notice what the fix was not: nobody weakened the contract to make the error go away. The API really sends _id; the mapper was wrong; the mapper changed.

  7. Watch the two halves meet. Reload the browser tab, and look at the recent-quotes panel: six quotes, ids q1 through q6. Those rows traveled from MongoDB through Express, through the proxy, into React state, onto your screen. Now the payoff the program has been missing since Phase 2: fill in a quote, click Save this quote, and reload the page. It is still there. The program’s first persistent quote. Say it at the sponsor check-in exactly that way.

  8. Observe the rate drift. Set the form to an auto quote, age 35, coverage amount 50000. The estimate box shows $425.00. Save it, and read the saved row at the top of the panel: $450.00/mo. Same inputs, two answers, and nothing is broken: the estimate is the client’s local math, still on the Phase 2-era rates (auto 85 / home 130 / life 65), while the saved premium is computed by the API on the standardized rates from last week (auto 90 / home 135 / life 70). Yesterday the two rate tables could not disagree in front of you, because the two halves never met. Today they can, and do. This is the drift the sponsor’s Monday instruction resolves, in the next block.

Example 2. Optional challenge: renters coverage end to end (the flagship: two languages, two validation systems)

Last week, renters coverage was deferred as scope-creep. It is still on the wish list, and now the wish crosses the whole stack. Add it end to end, and let each layer’s contract tell you where the change reaches.

  1. In client/src/types.ts, extend the union: export type CoverageType = "auto" | "home" | "life" | "renters"; and save. Run npm run type-check: it fails, because BASE_RATES in premium.ts no longer satisfies Record<CoverageType, number>. The compiler is walking you through the client-side cost of the change.

  2. In client/src/premium.ts, add renters: 40, to BASE_RATES. Type-check is clean again.

  3. In client/src/components/QuoteForm.tsx, add <option value="renters">Renters</option> to the coverage-type select.

  4. In api/src/premium.js, add renters: 40 to the API’s BASE_RATES (the same number on both sides; after this morning you know exactly why).

  5. Now save one renters quote before touching the database contract. In the browser, quote renters coverage and click Save this quote. It fails. Open dev tools (F12), Network tab: the POST to /api/quote returned 400, and the response body names the rule: the Mongoose schema’s enum for type does not include renters. TypeScript let this request leave the browser; the database contract refused it at the door. Two validation systems, and you found the line where one ends and the other begins.

  6. In api/src/Quote.js, add "renters" to the enum array. The API dev server restarts itself on save. Save the renters quote again: accepted, persisted, and at the top of the list after a reload.

Five files, two languages, two validation systems, one field. Optional, but nothing else this week shows the reach of a "small" product ask more honestly.
