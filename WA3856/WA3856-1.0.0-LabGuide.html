Evergreen Insurance Quote Page — Adding Types with TypeScript, NPM, and Vite

Lab 1

In this lab, you will take the Evergreen quote logic from last week’s JavaScript lab and move it into a real TypeScript project — managed by NPM and run with Vite. The app already works. Your job is to add the types that turn it from "hope it’s right" into "the compiler checked it for you."

You are not expected to master TypeScript’s type system. You are here to see what types do: catch mistakes before code runs, power the autocomplete your engineers rely on, and serve as a contract between the pieces of an app.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser. If a keyboard shortcut doesn’t reach the VM, use the mouse/menu alternative listed next to it.

1.2. Why You’re Doing This Lab

When your engineers say "TypeScript caught it," "that’s a type error," or "the build is red," they are describing the safety net you are about to install. After this lab, a pull request that adds an interface or a : number will read like something you have done, not something mysterious.

This lab also shows you the everyday toolchain — npm install, npm run dev, npm run build — that sits under every modern front-end project at Liberty Mutual.

1.3. What’s Already Set Up on Your Lab VM

  • Visual Studio Code with TypeScript support built in.

  • Node.js and NPM — already installed; check with node -v and npm -v.

  • The starter project: the same Evergreen quote app, now split into TypeScript modules under src/.

1.4. Open the Project and Install Packages

  1. Open a terminal (Terminal icon in the dock, or Ctrl+Alt+T).

  2. Go into the lab folder and open it in VS Code:

    cd ~/Labfiles/evergreen-quote-typescript-build
code .

  3. Install the project’s packages. This reads package.json and downloads TypeScript and Vite into a node_modules folder:

    npm install

    Why this matters: package.json is the project’s manifest. npm install is how every engineer sets up a project they just cloned. The node_modules folder it creates is never committed — it is rebuilt from package.json on each machine.

  4. Start the dev server:

    npm run dev

    Vite prints a local URL (usually http://localhost:5173). Ctrl+Click it, or open it in Chrome. The Evergreen quote page appears and the estimate already updates as you type.

 Note

npm run dev runs the "dev" script from package.json. Look at the "scripts" section — dev, build, and preview are just named shortcuts for longer commands.

1.5. See the Problem TypeScript Solves

  1. In VS Code, open src/premium.ts.

  2. Notice the red squiggly underlines. Hover over one. In premium.ts, TypeScript reports two things: CoverageType is imported from ./types but isn’t defined there yet — "Module './types' has no exported member 'CoverageType'" — and the function parameters (type, age, coverageAmount) implicitly have the any type. The same "no exported member" error appears for Quote in src/sampleQuotes.ts and src/main.ts, which import that type the same way.

  3. The app still runs in the browser — Vite’s dev server strips types and runs the plain JavaScript. The type errors only stop you at build time. Prove it. In a new terminal, run:

    npm run build

    The build fails with a list of type errors. That red is the safety net doing its job.

Why this matters: This is the core trade leaders need to understand. TypeScript adds a step that refuses to ship code whose types don’t line up. It is friction on purpose — friction that catches a whole category of bugs before a customer ever sees them.

1.6. Define the Types

  1. Open src/types.ts. Replace the entire contents of the file — the comments and the placeholder export {} line — with:

    export type CoverageType = "auto" | "home" | "life";

export interface Quote {
  id: number;
  type: CoverageType;
  age: number;
  coverageAmount: number;
  monthlyPremium: number;
}

  2. Save the file.

What you just wrote:

  • CoverageType is a union type — a value that must be exactly one of three strings. Misspell "home" as "hom" anywhere and TypeScript flags it.

  • Quote is an interface — a contract describing the shape of a saved quote. Any object claiming to be a Quote must have all five fields, with the right types.

    1. Look at src/sampleQuotes.ts. The red underline is gone — TypeScript now knows each object matches Quote.

Why this matters: : number and : CoverageType are the contracts. The : number after the parentheses is the return type — TypeScript will now complain if this function ever returns anything but a number.

1.8. Watch TypeScript Catch a Bug

  1. Open src/main.ts. Find the line that calls calculatePremium (around line 29). Temporarily break it by passing the age as a string:

    const premium = calculatePremium(type, "thirty-five", coverageAmount);

  2. Look at the editor: a red underline appears immediately on "thirty-five". Hover it — TypeScript says a string is not assignable to a parameter of type number. You found the bug without running anything.

  3. Undo that change (Ctrl+Z, or Edit > Undo) so the line is correct again.

Why this matters: In plain JavaScript, that bug would have produced NaN on a customer’s screen. In TypeScript, it never compiles. This is the single clearest answer to "why do we use TypeScript?"

1.9. Build for Production

  1. With all the types in place, run the build again:

    npm run build

  2. This time it succeeds. The "build" script runs tsc (the type-checker) first; only if every type lines up does Vite produce the optimized output in a dist/ folder.

  3. Preview the production build:

    npm run preview

Why this matters: A green build is the gate. When a leader hears "the build is passing," it means the type contracts hold across the whole project — exactly the assurance you just earned.

1.10. Review

In this lab you:

  • Used NPM to install dependencies and run scripts (npm install, npm run dev, npm run build).

  • Defined a union type and an interface to describe your data.

  • Added type annotations to function parameters and return values.

  • Watched TypeScript catch a bug in the editor, before running the code.

  • Produced a green production build with Vite, gated by the type-checker.

You took working JavaScript and gave it a safety net — the same move your engineers make on every serious front-end project, and the foundation for the React work coming next in Phase 2.

  1. Open a terminal (Terminal icon in the dock, or Ctrl+Alt+T).

  2. Go into the lab folder and open it in VS Code:

code .

  3. Install the project’s packages. This reads package.json and downloads React, Vite, and TypeScript into a node_modules folder:

2.5. Watch Hot Module Replacement (HMR)

  1. With the dev server running and the page open, click Count a view a few times so the counter shows a number greater than zero.

  2. The tagline on the page comes from the TAGLINE constant in src/branding.ts — App.tsx renders it as <p className="tagline">{TAGLINE}</p>. In VS Code, open src/branding.ts and change that text, for example:

    export const TAGLINE = "Coverage that grows with you — now with Vite";

  3. Save the file (Ctrl+S, or File > Save) and look at the browser.

  4. The page updates instantly — no full reload — and the counter keeps its value, even though the edit was in a different module.

Why this matters: That is Hot Module Replacement. Vite swaps only the module you changed, and React Fast Refresh re-renders the component that uses it while preserving the page’s state — so your counter survives. This tight feedback loop is a big part of why engineers are productive in a modern toolchain — and why "the dev server is down" is a real problem, not a minor one.

2.6. Read the npm Scripts

  1. Open package.json and look at the "scripts" section:

    "scripts": {
  "dev": "vite",
  "build": "tsc && vite build",
  "preview": "vite preview"
}

  2. Match each script to what it does:

    • dev — starts the dev server you are running now.

    • build — type-checks with tsc, then has Vite bundle and optimize for production.

    • preview — serves the finished production build locally so you can sanity-check it.

Why this matters: npm run <name> just runs the command on the right. These three names are the same in almost every Vite project, so once you know them here, you know them everywhere.

2.7. Build for Production and Inspect dist/

  1. Stop the dev server (Ctrl+C in the terminal), then run the production build:

    npm run build

  2. Look at the new dist/ folder:

    ls -R dist

    You will see an index.html and an assets/ folder containing files with names like index-DLniFmw2.js and index-C49dxfbv.css.

  3. Serve the production build to confirm it works:

    npm run preview

Why this matters: dist/ is exactly what gets deployed to a web server — nothing else. The scrambled part of each filename is a content hash: change the code and the name changes, so browsers never serve a stale cached file. Tree-shaking has also dropped any code the app didn’t use.

2.8. Add an Environment Variable

  1. In the project root (next to package.json), create a new file named .env with this content:

    VITE_APP_TITLE=Evergreen Insurance — Get a Quote

  2. Open src/App.tsx. Find the line that sets the title:

    const appTitle = COMPANY;

    Change it to read the environment variable, with the company name as a fallback:

    const appTitle = import.meta.env.VITE_APP_TITLE ?? COMPANY;

  3. Stop and restart the dev server (Ctrl+C, then npm run dev) — Vite reads .env files at startup. The heading now shows the title from the .env file.

Why this matters: Configuration that changes between environments — an API address, a feature flag, a title — lives in .env files, not in the code. The VITE_ prefix is a safety gate: only prefixed variables are exposed to the browser, so a secret without the prefix can’t leak into the shipped app.

2.9. Add a Path Alias

  1. Open vite.config.ts and add a resolve.alias entry so @ points at the src/ folder:

    import { defineConfig } from "vite";
import react from "@vitejs/plugin-react";
import path from "path";

export default defineConfig({
  plugins: [react()],
  resolve: {
    alias: {
      "@": path.resolve(__dirname, "./src"),
    },
  },
});

  2. Open tsconfig.json and tell TypeScript about the same alias so it can still check the types. Add these two keys inside "compilerOptions":

    "baseUrl": ".",
"paths": {
  "@/*": ["src/*"]
}

  3. Open src/App.tsx and change the branding import from a relative path to the alias:

    import { COMPANY, TAGLINE } from "@/branding";

  4. Restart the dev server (Ctrl+C, then npm run dev). The page still works — the import now resolves through the alias.

Why this matters: Aliases replace fragile relative paths like ../../../utils/format with clean, stable ones like @/utils/format. Moving a file no longer breaks its imports. Note that the alias has to be declared twice — once for Vite (which runs the code) and once for TypeScript (which checks it).
