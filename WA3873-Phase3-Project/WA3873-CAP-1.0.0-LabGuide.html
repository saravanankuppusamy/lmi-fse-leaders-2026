Phase 3 Capstone Project for Leaders

Phase 3 Capstone: Lead & Assemble the Evergreen Quote API Delivery

Lab 1

In this capstone, you will spend four days as the Delivery Lead for Evergreen Insurance Quote, the same product you have followed all program: first a static page, then a live one, then a React app, and now, in Phase 3, a product with a back end. The engineering team has been building the Evergreen Quote API: an Express + Mongoose service that speaks REST for the website and GraphQL for partners, stores quotes in MongoDB, and ships the way the engineering organization ships real services: tested in a pipeline, packaged in a container, and run on Kubernetes. You start from a starter project provided in your lab kit (a running service shell with a health route, a database connection, and a test suite) and, over the week, expand it into the working, shippable service by assembling the provided pieces: the quote routes, the GraphQL layer, the container recipe, the CI workflow, and the cluster manifests. You will lead a simulated four-day delivery week while you do it. On Friday you will present what your team delivered and run a lessons-learned review.

You will not write code from scratch. Every coding step in this capstone is an assembly step: push the starter to your own repo, branch, seed the database from the database shell, drop in a provided module, paste the kit’s wiring lines at a marker, configure a value, apply a provided one-line fix, build an image, enable a workflow, apply manifests, open a PR. The skill being practiced is leading delivery, not authoring software.

Writing code is never required to complete this capstone. But if you want to get hands-on, several assembly blocks include a short, clearly-marked optional challenge: a small, self-contained change you can try. Across the week these cover inserting a document by hand in the database shell (MongoDB), pasting a new test and making it fail on purpose (Node), breaking and restoring the Docker layer cache (Docker), and scaling and self-healing the cluster (Kubernetes). They are entirely optional; skipping them costs you nothing and does not affect completion.

 Tip

This capstone is the culmination of every Phase 3 topic (AI-assisted code with tests as the safety net, Node.js and Express, REST and GraphQL, MongoDB documents and mongosh, Mongoose validation and Express-database integration, cloud deployment to S3, containerization with Docker, orchestration with Kubernetes) plus the Git, GitHub, and CI/CD working method you carry over from Phases 1 and 2. You will touch each one as a leader, not as an engineer.

1.3. Before You Start: Environment Check

  1. Confirm the lab kit is on your VM:

    ls ~/Labfiles/wa3873-cap-phase-3-capstone-project-leaders

    You should see folders named starter/, data/, api-routes/, graphql/, containerize/, workflows/, site/, deploy/, k8s/, and templates/, plus an empty delivery-leadership-package/ scaffold and the kit README.md. The first set are the provided pieces you will assemble from; delivery-leadership-package/ is where your written leadership artifacts will go.

  2. Confirm the starter project is present and runs on your VM. It is the engineering team’s baseline: the service you will lead and assemble onto this week:

    cd ~/Labfiles/wa3873-cap-phase-3-capstone-project-leaders/starter
npm install
npm run dev

    The first command installs the team’s pinned dependencies from the lock file (about a minute); the second starts the API and prints Connected to MongoDB: mongodb://127.0.0.1:27017/evergreen. In a second terminal, run curl http://localhost:3000/. It answers {"message":"CHANGEME - set the service name in .env","status":"ok"}. The service is up, and it does not know its own name. That is real, and it is yours to deal with this week. Press Ctrl+C in the first terminal to stop the server.

     Tip

    If the server fails to start with Error: listen EADDRINUSE: address already in use :::3000, another process already owns port 3000. If it is a dev server still running in another terminal (or, on Day 3, the container), press Ctrl+C there. If no terminal of yours is running one, the owner can belong to another user, so look with sudo, then free the port and start again:

    sudo ss -ltnp 'sport = :3000'
sudo fuser -k 3000/tcp
npm run dev

    The ss command names the process holding the port; fuser -k stops it. If the port becomes busy again on its own, the owner is a managed service that restarts itself — a Docker container (docker ps, then docker stop <id>) or a system service — so stop it at its source, or ask the instructor. This fix applies any time this week the server refuses to start with that error.

  3. Confirm the week’s three platforms answer. You are not collecting version numbers; you are observing that each one responds:

    mongosh --quiet --eval "db.runCommand({ ping: 1 })"
docker version
kind version

    The ping returns { ok: 1 }: the database the API talks to is up. docker version prints a client and a server section: the engine that builds Wednesday’s image is running. kind version prints a version line: the local Kubernetes that hosts Thursday’s demo is installed. If anything fails, ask the instructor before proceeding.

     Note

    You are not writing Express code. You are pasting provided lines in the right slots and saving; --watch restarts the server for you.

  2. Read through the API. Take the curl tour of what your engineers built:

    curl http://localhost:3000/api/quotes
curl http://localhost:3000/api/quotes/q1

    The first returns six quotes: the exact documents you seeded and inspected on Monday. The API is not making data up; it is reading your database. The second returns one: {"_id":"q1","type":"auto","age":41,"coverageAmount":50000,"monthlyPremium":96,"tags":["renewal"]}. One detail worth a leader’s eye: the seeded quotes have no createdAt. They were inserted by mongosh, so Mongoose’s timestamps never ran. Quotes created through the API get createdAt, updatedAt, and a UUID _id. Same collection, two provenances; you will see the difference in the next step.

  3. Create a quote, then watch validation guard the door.

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"auto","age":35,"coverageAmount":50000}'

    A 201 with a full quote document: UUID id, timestamps, and a computed monthlyPremium. It looks fine. Note the premium number anyway; keep it in mind. Then send a quote the schema should refuse (same POST, but "age":5):

    {"error":"Quote validation failed: age: Path `age` (5) is less than minimum allowed value (18)."}

    Read that message out loud, in plain English: the Mongoose schema, Week 5’s contract, rejected the write before it reached the database and named the field, the value, and the rule. Try "type":"boat" the same way: another 400, naming boat as not a valid value for type. Then fetch an id that does not exist (curl http://localhost:3000/api/quotes/does-not-exist): a 404 with {"error":"Not found"}. Every door is guarded.

  4. Now ask the safety net. The demo looked good. Ask the tests whether it is good: run npm test. Seven tests run. Six pass. Exactly one fails: POST /api/quote computes the premium with the shared rate table, showing 0.35 !== 400 (actual vs. expected). Scroll back to your own 201: the premium in it was 0.35. Thirty-five cents a month for $50,000 of coverage. The demo lied; the tests did the math. This is the AI-drafted handler from the file header, and exactly the failure Week 1 warned about: code that reads plausibly and computes wrongly.

  5. Apply the kit’s one-line fix. You are not debugging; the engineering team already has the fix, and the kit README.md ("Day 2: the one-line route fix") shows the exact before/after. In src/routes.js:

    // Before (the AI-drafted line):
const monthlyPremium = calculatePremium(type, Number(coverageAmount), Number(age));
// After (the kit's fix):
const monthlyPremium = calculatePremium(type, Number(age), Number(coverageAmount));

    The handler passed the premium inputs in the wrong order. Run npm test again: all seven pass. Re-run the same POST from the curl tour: 201 again, but now "monthlyPremium":400 at the starter rates. Same request, same tidy status code, different truth. One more leader note: the $0.35 quote from before the fix is still in the database. Bad data outlives bad code; log it (Thursday’s seed reset clears it).

Example 3. Optional challenge: break the layer cache on purpose (a little Docker)

The dependency layer is cached because the package files are copied before the source. Break that ordering and watch what it costs.

  1. In your Dockerfile, move COPY . . above the package-file copy and install, so the middle reads:

    COPY . .
COPY package.json package-lock.json ./
RUN npm ci --omit=dev

  2. Rebuild: the full dependency install runs again, because the source copy now sits above it and invalidates it. Add another blank line to src/index.js and rebuild once more: another full reinstall. Every save now costs the whole install; Week 7’s lesson, run in reverse.

  3. Restore the provided order (package files, then RUN npm ci --omit=dev, then COPY . .), rebuild, edit, rebuild again, and watch CACHED return on the install layer.

This is optional. Skipping it costs you nothing.

     Note

    The mongo:7 load often fails with ERROR: failed to load image: …​ ctr: content digest sha256:…​: not found. Ignore it and continue.
