Evergreen Insurance Quote Page — Live Premium Estimate with JavaScript

Lab 1

In this lab, you will take the Evergreen Insurance Quote Page you styled in Phase 1 and bring it to life with JavaScript. Right now the page is static: the form looks good but does nothing. By the end of this lab the page will calculate a monthly premium as the user types, validate the inputs, and load a list of recent quotes from a data file — all in the browser.

You are not expected to memorize JavaScript syntax. You are here to recognize the building blocks your engineers use every day — functions, the DOM, events, error handling, and asynchronous code — by wiring them together on a page you already know.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser. Some keyboard shortcuts (like Ctrl+S or Ctrl+F) may not always reach the VM — sometimes your browser catches them first. If a shortcut doesn’t do anything, that’s not you doing something wrong; just use the mouse/menu alternative that appears next to every shortcut in this lab.

1.2. Why You’re Doing This Lab

Every interactive feature your engineers ship — a price that updates live, a form that rejects bad input, a list that loads without a page refresh — is built from the same handful of JavaScript concepts. When you have wired them together once yourself, code review comments like "move this into a function," "that’s a DOM update," or "this needs a try/catch" stop being jargon and start being things you have done.

This lab walks you through that exact transformation on the Evergreen Quote Page: from a page that just sits there to one that responds instantly to the user.

1.7. Calculate the Premium

Each function in app.js starts as a stub — the function line, a few TODO comments, and a closing }. In every step below, replace the entire stub (including the function …() { line and its closing }) with the version shown. Replace it over the stub — don’t paste the new code beside it, or you’ll end up with the same function defined twice and the browser will use the wrong one.

Find the calculatePremium stub. Select the whole thing — from its function line down to its closing } — and replace it with this:

function calculatePremium(type, age, coverageAmount) {
  const base = BASE_RATES[type] ?? 100;
  const ageFactor = age < 25 ? 1.4 : age > 60 ? 1.25 : 1.0;
  const coverageFactor = coverageAmount / 10000;
  return base * ageFactor * coverageFactor;
}

What each line does:

  • BASE_RATES[type] looks up the base rate using bracket notation (the type is dynamic). The ?? 100 is the nullish coalescing operator — a fallback used only when the lookup is missing.

  • ageFactor uses a ternary to pick a multiplier based on age.

  • The function returns a value instead of touching the page. That separation — calculate here, display elsewhere — is a habit that makes code testable.

1.8. Validate the Inputs

Find the validateInputs stub and replace the whole thing so bad input fails fast with a clear message:

function validateInputs(age, coverageAmount) {
  if (Number.isNaN(age) || age < 18 || age > 100) {
    throw new Error("Please enter an age between 18 and 100.");
  }
  if (Number.isNaN(coverageAmount) || coverageAmount < 10000) {
    throw new Error("Coverage amount must be at least $10,000.");
  }
}

Why this matters: throw new Error(…​) stops the function and hands a clear message to whoever called it. This is how engineers make invalid states impossible instead of letting bad data flow downstream.

1.9. Show a Live Estimate

Find the updateEstimate stub and replace the whole thing. This function reads the form, validates it, calculates the premium, and shows the result — or shows the error if validation fails:

function updateEstimate() {
  const type = typeEl.value;
  const age = Number(ageEl.value);
  const coverageAmount = Number(amountEl.value);

  try {
    validateInputs(age, coverageAmount);
    const premium = calculatePremium(type, age, coverageAmount);
    estimateEl.textContent = formatCurrency(premium);
    messageEl.textContent = "";
    messageEl.classList.remove("success");
  } catch (error) {
    estimateEl.textContent = "—";
    messageEl.textContent = error.message;
    messageEl.classList.remove("success");
  }
}

Notice the try / catch: if validateInputs throws, execution jumps straight to catch, and the page shows the message instead of crashing.

1.10. Wire Up the Events

Scroll to the bottom of the file, to the "Wire everything up" section. These last TODO`s are plain comments — there is no function stub here — so just replace the comment lines with the code below. (You’ll add the final line, the call to `loadRecentQuotes(), in the next section.)

updateEstimate();

form.addEventListener("input", updateEstimate);

form.addEventListener("submit", (e) => {
  e.preventDefault();
  updateEstimate();
  if (!messageEl.textContent) {
    messageEl.textContent = "Quote saved. An agent will follow up shortly.";
    messageEl.classList.add("success");
  }
});

What this does:

  • updateEstimate() runs once so the page shows a number immediately.

  • The "input" listener re-runs it on every keystroke or dropdown change — that is what makes the estimate feel "live."

  • The "submit" listener calls e.preventDefault() to stop the browser’s default "reload the page" behavior, then shows a confirmation.

 Note

"Quote saved" is a message, not actual saving. The JavaScript in this lab runs entirely inside the browser, and browser JavaScript is deliberately sandboxed — it cannot write to your computer’s file system or update quotes.json. Reload the page and the quote is gone. To truly persist a quote, the browser would send it to a server that runs code outside the browser — such as a Node.js backend — which then writes it to a file or database. That server-side half of JavaScript is covered later in the course. For now, just notice the boundary: the browser handles what the user sees and does; saving real data is a server’s job.

  1. Save the file. Two ways:

    • From the menu: File > Save.

    • With a keyboard shortcut: Press Ctrl+S.

  2. Switch to the browser. Live Server reloads automatically. Change the age to 22, then to 65, then change the coverage amount. The estimate updates as you type.

Why this matters: You just connected a user action (typing) to code (your functions) through an event listener. Every button, field, and menu in every app your teams build is wired exactly this way.

1.11. Load Recent Quotes Asynchronously

The "Recent quotes" panel is still stuck on "Loading…". It needs data from quotes.json. Find the loadRecentQuotes stub and replace the whole thing:

async function loadRecentQuotes() {
  try {
    const response = await fetch("quotes.json");
    if (!response.ok) {
      throw new Error(`HTTP ${response.status}`);
    }
    const data = await response.json();
    renderRecentQuotes(data);
  } catch (error) {
    recentList.innerHTML = `<li class="error">Could not load recent quotes.</li>`;
    console.error("Failed to load recent quotes:", error.message);
  }
}

Then find the renderRecentQuotes stub and replace the whole thing:

function renderRecentQuotes(quotes) {
  recentList.innerHTML = "";
  quotes.forEach((quote) => {
    const li = document.createElement("li");
    li.innerHTML = `
      <span class="quote-type">${quote.type}</span> &mdash;
      <span class="quote-premium">${formatCurrency(quote.monthlyPremium)}/mo</span>
    `;
    recentList.appendChild(li);
  });
}

Finally, just below the event listeners at the bottom of the file (last line of your script), call it:

loadRecentQuotes();

  1. Save the file and switch back to the browser.

  2. The "Recent quotes" panel now lists four quotes with their monthly premiums. The "Loading…" message is gone.

Why this matters: async / await lets the page ask for data and keep responding while it waits — no frozen screen. This is the same pattern behind every list, dashboard, and search result your engineers build. The try / catch means a failed request shows a friendly message instead of a blank panel.

1.12. Break It on Purpose

  1. Switch to VS Code.

  2. In the Explorer, rename quotes.json to quotes-broken.json (right-click → Rename).

  3. Save and reload the page. The recent-quotes panel now reads "Could not load recent quotes," and the Console shows your console.error message — but the rest of the page still works. The premium estimate still updates.

  4. Rename the file back to quotes.json.

Why this matters: You just saw the difference between an app that handles failure and one that falls over. When a leader asks "what happens if the data service is down?", this — a contained, friendly failure — is the answer engineers are designing toward.

1.13. Review

In this lab you:

  • Wrote a pure function that calculates a premium and returns a value.

  • Used an object as a lookup table and bracket notation to read it.

  • Selected and updated DOM elements to show results on the page.

  • Connected user actions to your code with event listeners and preventDefault().

  • Used try / catch and a thrown Error to validate input and fail gracefully.

  • Loaded data with async / await and fetch, then rendered it into the page.

You turned a static page into an interactive one using the same JavaScript building blocks your engineers reach for every day — and you saw, firsthand, why "put it in a function" and "wrap it in a try/catch" are such common review comments.
