AI Code Generation with GitHub Copilot and LibertyGPT for Leaders

Evergreen Insurance — Building Features with AI Assistance, Responsibly

Lab 1

In this lab, you will add features to the Evergreen codebase with GitHub Copilot and, just as importantly, you will review what the AI produces. You will work the way your engineers do: inline code completions plus all four of Copilot’s chat modes (Ask, Edit, Plan, and Agent). AI coding tools are fast and impressive, but they also confidently produce code that is subtly wrong. The skill that matters most for a leader is not generating code; it is knowing how to direct an AI well and how to verify its output.

You are not expected to become a prompt-engineering expert. You are here to experience the AI-assisted workflow your engineers now use every day, and to feel why "accept, inspect, edit, test" is the only safe way to use these tools. Everything you practice with Copilot here applies equally to Liberty GPT and any other approved assistant.

1.1. A Note About Keyboard Shortcuts

If a keyboard shortcut doesn’t reach the VM, use the mouse/menu alternative listed next to it.

1.2. Why You’re Doing This Lab

Your teams are already coding with AI. The leadership questions are no longer "should we?" but "how do we use this well, safely, and accountably?" After this lab you will have generated code from a prompt, caught an AI-introduced bug, spotted a hallucinated API, reviewed an AI’s plan before letting it write code, delegated a task to an autonomous agent, and verified everything with tests: exactly the discipline you want your organization to practice.

  2. In VS Code, open the integrated terminal: menu Terminal > New Terminal. It opens directly in the project folder. Run the tests there:

     Important

  3. Most of the tests fail right now because the exercises aren’t done. That red is your checklist. You will re-run node --test in the integrated terminal after each step.

1.6. Exercise 1: Generate From a Clear Specification (Completions)

  1. Open evergreen-features.js and read the spec comment above applyMultiPolicyDiscount; it states the rules, the rounding, and the return type.

  2. Place your cursor on a blank line inside the function body (TODO 1) and pause. Copilot’s ghost-text suggestion appears. Read it before pressing Tab: does it implement exactly the tiers, the rounding, and the return type the spec names? If the first suggestion is partial, accept it and pause for the next one, or start typing let rate to steer it. Here is one correct implementation:

    let rate = 0;
if (policyCount === 2) rate = 0.1;
else if (policyCount >= 3) rate = 0.15;
const discounted = premium * (1 - rate);
return Math.round(discounted * 100) / 100;

  3. Don’t expect your suggestion to match that word for word; Copilot rarely produces the same code twice. It often proposes an equivalent variant like this one, which is also correct:

    if (policyCount === 2) {
  premium *= 0.9;
} else if (policyCount >= 3) {
  premium *= 0.85;
}
return Math.round(premium * 100) / 100;

    Same tiers, same rounding, same return type; it just multiplies by 0.9/0.85 instead of subtracting a rate. Judge a suggestion by its behavior against the spec, not by whether it resembles someone else’s code. The tests are the referee.

  4. Run node --test. The applyMultiPolicyDiscount tests should now pass.

Why this matters: A precise comment is a precise prompt. Notice how the spec named the rules, the rounding, and the return type, leaving Copilot nothing important to guess. Vague requests produce vague code.

1.7. Exercise 2: Catch an AI-Introduced Bug (Ask Mode)

The formatQuoteSummary function is exactly what an AI assistant produced for a reasonable prompt. It looks right. It even runs. But it is wrong.

  1. Run node --test and read the failing formatQuoteSummary expectation; it expects "AUTO — $96.00/mo".

  2. Before you fix anything, use Copilot as a diagnostic partner. Select the whole function, open the Chat view (Ctrl+Alt+I), make sure the mode dropdown says Ask, and send:

    This function should return "AUTO — $96.00/mo" for
{ type: "auto", monthlyPremium: 96 }, but a test says it doesn't.
What exactly is wrong with it?

  3. Read the answer critically and confirm every claim against the code yourself (TODO 2). Two problems hide in plain sight:

    • quote.type.toUpperCase references the function but never calls it (missing ()).

    • The premium isn’t formatted to two decimals.

  4. Ask mode never edits files, so make the fix yourself:

    const type = quote.type.toUpperCase();
const premium = "$" + quote.monthlyPremium.toFixed(2) + "/mo";
return `${type} — ${premium}`;

  5. Re-run node --test; it passes.

Why this matters: This is the single most important lesson of the week. AI-generated code can be plausible and broken at the same time. The missing () is the kind of error that slips past a quick glance and into production. Notice what just happened: an AI wrote the bug and an AI helped diagnose it, but a human confirmed the diagnosis, made the fix, and owns the result. Tests, and a careful human read, are what catch it.

1.8. Exercise 3: Spot the Hallucination (Ask Mode)

  1. Look at parseAmount (TODO 3). The AI suggested Number.parseMoney(text). It sounds real. It is not; there is no such function in JavaScript. This is a hallucination: the model inventing an API that doesn’t exist.

  2. Ask Copilot to check its own kind of mistake. In Ask mode, send:

    Is Number.parseMoney a real JavaScript API? If not, what real code
parses a currency string like "$1,250.50" into the number 1250.5?

    Asked directly, the model will usually debunk the very API it happily invents while completing code. The final authority is still real documentation (MDN) and your tests, never the model’s confidence.

  3. Replace the invented call with real parsing logic:

    return Number(text.replace(/[$,]/g, ""));

  4. Run node --test. Everything except the quoteBundleTotal tests should pass now (those are Exercises 7 and 8).

Why this matters: Models trained to predict "plausible next code" will sometimes invent functions, libraries, or options that were never real. When an engineer says "Copilot hallucinated an API," this is it. The fix is always the same: verify against real documentation.

1.9. Exercise 4: Write a Strong Prompt, Then Prove It’s Stronger (Ask Mode)

  1. Open prompts.md. A teammate’s prompt was simply "make a discount function." Rewrite it as a strong prompt using the four parts: Context, Task, Constraints, Format (Exercise 4 in the file).

  2. Now run the experiment. In Ask mode, send the weak prompt exactly as written:

    make a discount function

    Look at what comes back: some language, some rules, some shape, all guessed.

  3. Start a new chat (the + button in the Chat view) and send your improved prompt. Compare the two results. Which one could you paste into the codebase and verify against test.mjs without edits?

  4. Compare your prompt with prompts.solution.md. Notice how the strong prompt names the language, the exact rules, the rounding, and the return type, so the output is both better and easy to verify.

Why this matters: The quality of AI output is mostly determined by the quality of the prompt. You just watched the same model produce guesswork or near-production code depending entirely on what it was given. Teaching your teams to write specific, constrained prompts is one of the highest-leverage things a leader can encourage.

1.10. Exercise 5: Interrogate Code You Didn’t Write (Ask Mode)

Scroll to riskTier in evergreen-features.js. It works, and its tests already pass. It is also a one-line nest of ternaries that nobody wants to decode by hand. Treat it as code your team inherited.

  1. Select the riskTier function. In Ask mode, send:

    Explain exactly what this function returns for every possible
score, as a table of ranges. Include the boundary values.

  2. Verify the answer against reality: open test.mjs and find the riskTier test. Do the boundaries Copilot described (80, 65, 50) match the assertions? If the explanation and the tests disagree, trust the tests and ask again.

  3. Ask one follow-up:

    Which boundary values would be most important to unit test here?

    Compare its suggestions with the assertions that already exist. Asking an AI "what tests are missing?" is a fast way to find blind spots in real code.

Why this matters: Engineers spend far more time reading code than writing it. Ask mode turns opaque legacy code into something you can question in plain English: enormous leverage for onboarding, code review, and system archaeology. But its explanation is a claim, not a fact, which is why you verified it against the tests.

1.11. Exercise 6: Refactor With a Safety Net (Edit Mode)

You understand riskTier now. Time to make the next reader’s life easier, without changing what the function does.

  1. In the Chat view, switch the mode dropdown to Edit. Keep evergreen-features.js open; Edit mode works on the files you give it, and the open file is attached automatically (or use Add Context to attach it). Send:

    Refactor the riskTier function into readable if/else statements
with early returns (TODO 6). Do not change its behavior or its
export. Keep the same tier names and boundaries.

  2. Copilot proposes the change as a diff in the editor. This is the point of Edit mode: nothing lands until you review it. Read the diff. Are the boundaries still >= 80, >= 65, >= 50? Is the export unchanged?

  3. Accept the change (Keep), then prove the refactor is safe:

    node --test

    The riskTier tests still pass: behavior preserved, readability improved. If anything went red, undo the edit and try again with a more constrained prompt.

Why this matters: Refactoring with an AI is only safe when two things are true: a human reviews the diff, and tests pin the behavior. You had both. "Never accept a refactor without a safety net" is a rule worth repeating to your teams.

1.12. Exercise 7: Review the Plan Before the Code (Plan Mode)

Evergreen wants a bundle feature: total the monthly premiums for a set of quotes and apply the multi-policy discount. The spec is written above quoteBundleTotal in evergreen-features.js (TODO 7 & 8). You will not write this one by hand. First, make Copilot show its intentions.

  1. Switch the mode dropdown to Plan and send:

    Plan the implementation of quoteBundleTotal in evergreen-features.js,
following the spec comment above it. It must reuse
applyMultiPolicyDiscount rather than duplicating the discount rules,
and it must pass the existing tests in test.mjs. Planning only: do
not write the code yet.

  2. Copilot produces a step-by-step plan instead of code. Review it the way you would review a design document:

    • Does it reuse applyMultiPolicyDiscount, or does it quietly duplicate the discount tiers (a maintenance trap)?

    • Does it handle the empty array case with a RangeError, as the spec requires?

    • Does it end with running the tests?

  3. If the plan misses any of those, say so in chat ("The plan must reuse applyMultiPolicyDiscount; revise it") and review the revision. Fixing a plan costs seconds. Fixing merged code costs much more.

Why this matters: Plan mode moves human review to the cheapest possible moment: before any code exists. For non-trivial work, "show me the plan first" is the same discipline you already apply to architecture reviews, applied to AI.

1.13. Exercise 8: Delegate, Then Verify (Agent Mode)

Now let Copilot carry the plan out end to end: writing the code, running the tests, and reacting to failures on its own.

  1. Switch the mode dropdown to Agent and send:

    Implement quoteBundleTotal in evergreen-features.js according to the
spec comment and the plan we agreed. Reuse applyMultiPolicyDiscount.
Then run node --test and fix any failures you caused. Do not modify
test.mjs.

  2. Watch what happens. The agent edits the file, asks to run node --test in the terminal (approve it), reads the results, and iterates if something fails. This is the loop your engineers run all day, compressed.

  3. When the agent reports success, you take over:

    • Review the diff it produced before keeping it. Is the code what the plan promised? Is test.mjs untouched?

    • Run node --test yourself. Every test in the project should now pass.

  4. Note the last line of the prompt: Do not modify test.mjs. An agent optimizes for the goal it is given, and "make the tests pass" has one degenerate solution: change the tests. When tests are your safety net, put them explicitly out of bounds.

Why this matters: Agent mode is delegation, and delegation without verification is abdication. The agent is tireless and fast, but it has no accountability; the human who reviews and keeps the diff owns it. That review-then-own step is precisely the policy you want in your organization.

1.14. Responsible Use (Discussion)

Take a moment on the practices that make AI assistance safe in an enterprise like Liberty Mutual:

  • Human accountability: the engineer who commits AI-generated code owns it, exactly as if they wrote it by hand. That includes everything an agent produced.

  • Verify, always: run it, test it, and read it. AI output is a draft, whether it came from a completion, an edit, a plan, or an agent.

  • Scope your agents: state what must not change (tests, public contracts, other teams' code) and review every diff before it lands.

  • Never paste secrets: don’t put credentials, customer data, or proprietary code into a prompt unless the tool is an approved enterprise service (like Liberty GPT) cleared for it.

  • Licensing and provenance: be aware that suggestions can resemble training data; enterprise tools provide filtering and policy controls for this.

Why this matters: These are leadership concerns, not just engineering ones. The policies you set determine whether AI accelerates your teams safely or introduces risk.
