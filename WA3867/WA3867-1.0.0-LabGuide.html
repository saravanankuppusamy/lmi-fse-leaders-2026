WA3867 Lab Guide

Orchestration with EKS for Leaders

Evergreen Insurance Quote API: Orchestrating with Kubernetes, Locally and on Amazon EKS

Lab 1

In this lab, you will run the Evergreen API container on Kubernetes: the platform that keeps the right number of copies alive, replaces failed ones automatically, and rolls out new versions without downtime. You will do it twice. First on a local cluster running on your own lab VM, then on Amazon EKS, the managed Kubernetes service on AWS. The manifests you write are the same both times. Only the platform underneath changes.

This is Week 8, the final content week of Phase 3, and the last stop on a long road: the API you built in Week 2, explored in Week 3, backed with a database in Weeks 4 and 5, and containerized in Week 7 now runs the way production platforms run it.

Local first is not a shortcut. It is how teams work: prove the manifests on a throwaway cluster that costs nothing and starts in a minute, then apply those same files to the cloud. When the cloud deployment misbehaves, you already know the manifests are not the problem.

You are not expected to operate a Kubernetes cluster. You are here to read and understand the two manifests at the heart of nearly every deployment (a Deployment and a Service), to see the idea that makes Kubernetes powerful (you declare the desired state, and the platform makes reality match it), and to see what a managed cloud service adds on top.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

"Scale it to five replicas," "the pod is crash-looping," "do a rolling update," "self-healing kicked in," "it works on the local cluster but not in EKS": this is the language of running software at scale. After deploying the same app to two clusters yourself, each phrase becomes concrete, and you can reason about availability, scaling, portability, and the cost of running services.

1.3. What You Need

  • An AWS account you can sign in to, with permission to create an EKS cluster and an ECR repository. Your instructor provides the sign-in details.

  • AWS CLI credentials for that account (an access key ID and secret access key), or an already-configured CLI on your VM.

 Caution

Unlike the storage lab in Week 6, this lab is not free-tier work. It costs roughly $0.25 an hour while it runs, in four parts worth knowing: the EKS control plane (about $0.10 an hour, charged whether or not anything is deployed on it), the two virtual machines that run your pods, the load balancer, and a NAT gateway for the cluster’s private network. The cleanup section at the end removes all of it, and you need to run it.

1.4. What’s Already Set Up on Your Lab VM

  • VS Code, a terminal, and Docker (to build the container image).

  • kubectl, the Kubernetes command-line tool, which talks to any cluster.

  • kind, which runs a throwaway Kubernetes cluster inside Docker on this VM.

  • The AWS CLI and eksctl, the tool that creates EKS clusters.

  • The starter project: the Evergreen API source and Dockerfile from Week 7, plus k8s/deployment.yaml and k8s/service.yaml, each with `TODO`s.

1.5. Open the Project

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-eks in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-eks.

  4. Confirm the five tools you need are present. Each command prints a version line:

    docker --version
kubectl version --client
kind --version
eksctl version
aws --version

  5. Confirm the AWS CLI is connected to your account:

    aws sts get-caller-identity

    It prints an account number and an ARN. If it reports missing credentials, run aws configure and enter the access key ID and secret access key your instructor provides, us-east-1 for the default region, and json for the output format.

1.6. The Lab at a Glance

The lab runs the same app on two clusters, in eight moves:

  1. Start the EKS cluster building. It takes 15 to 20 minutes, so it runs in the background while you work.

  2. Build the image and create a local cluster with kind.

  3. Complete the Deployment (k8s/deployment.yaml, TODO 1-TODO 3): how many copies, which image, which port.

  4. Complete the Service (k8s/service.yaml, TODO 4-TODO 6): how traffic finds those copies and gets balanced across them.

  5. Deploy locally and watch self-healing and scaling.

  6. Push the image to Amazon ECR, the AWS container registry.

  7. Deploy the same manifests to EKS and call the API over the public internet.

  8. Clean up both clusters.

Think of the Deployment as the staffing order ("keep three licensed agents on duty at all times") and the Service as the single phone number customers call, which always reaches whichever agents are on shift.

 Tip

Every YAML snippet below replaces a numbered TODO comment; the comment states the value it expects, so the files double as an answer key. YAML cares about indentation: paste at the same indent level as the line the TODO sits on.

1.7. Start Your EKS Cluster Now

Creating an EKS cluster takes 15 to 20 minutes, so start it before anything else and let it build while you do the local half.

  1. Choose a name for your cluster. Cluster names have to be unique within the AWS account, so add something of your own, in lowercase letters, numbers, and hyphens:

    evergreen-your-initials-1234

    For example, evergreen-ae-2431. Write it down. You need it three more times in this lab.

  2. Open a second terminal beside the first (Terminal → Split Terminal, or Ctrl+Shift+5). Run the create command there, substituting your cluster name:

    eksctl create cluster \
  --name evergreen-your-initials-1234 \
  --region us-east-1 \
  --nodes 2 \
  --node-type t3.medium \
  --managed \
  --write-kubeconfig=false

  3. Leave that terminal running and go back to the first one. Do not wait for it. You come back to it later in the lab.

While it runs, eksctl builds a private network (a VPC with public and private subnets), the EKS control plane, two EC2 virtual machines to run your pods on, and the IAM roles that let all of it talk to itself. Each of those is a separate AWS resource with its own creation time, which is why the wait is minutes rather than seconds.

 Note

--write-kubeconfig=false matters more than it looks. Without it, eksctl would point kubectl at the new cloud cluster the moment it finished, silently, in the middle of your local work. You connect to EKS deliberately, later, when you are ready.

Why this matters: A local cluster starts in about a minute; a cloud cluster takes twenty. That gap is why teams do not create a cluster per deployment. They create long-lived clusters and deploy into them many times a day, which is exactly the pattern this lab imitates.

1.8. Understand Desired State

While EKS builds, fix the mental model. Kubernetes works by reconciliation: you declare what you want, and a control loop continuously works to match it.

  • A Pod is the smallest unit: one or more containers running together. Pods are disposable.

  • A Deployment declares how many pods of your app should exist and which image they run. If a pod dies, the Deployment starts a new one. This is self-healing.

  • A Service gives those ever-changing pods one stable address and load-balances across them.

Why this matters: You never start or restart pods by hand. You tell Kubernetes "I want three of these," and it is the platform’s job to keep three running, through crashes, node failures, and updates. That shift from "do these steps" to "maintain this state" is the core idea of orchestration.

1.9. Build the Image and Create a Local Cluster

The Evergreen API source and the finished Dockerfile from Week 7 are already in the lab folder, so you build the image rather than write it.

  1. In your first terminal, from the lab root, build the image and tag it with a version:

    docker build -t evergreen-quote-api:1.0 .

    The build runs one numbered step per Dockerfile instruction and finishes in a few seconds after npm install.

  2. Create the local cluster:

    kind create cluster --name evergreen

    kind starts a single-node Kubernetes cluster inside a Docker container and points kubectl at it. The output ends with Set kubectl context to "kind-evergreen".

  3. Confirm the cluster is up and that kubectl is talking to it:

    kubectl config current-context
kubectl get nodes

    The context is kind-evergreen, and one node reaches Ready within a few seconds.

  4. Now hand your image to the cluster:

    kind load docker-image evergreen-quote-api:1.0 --name evergreen

    It reports not yet present on node "evergreen-control-plane", loading…​ and finishes.

Why this matters: That last step is the one worth remembering. Your cluster could not see the image you had just built, because a cluster is a separate place from your laptop. Every cluster faces the same question, "where do I get this image from?", and there are only two answers: hand it over directly (what kind load does, and only a local cluster can), or publish it to a registry the cluster can pull from. EKS gets the second answer later in this lab. That is the entire reason container registries exist.

1.10. Complete the Deployment

Open k8s/deployment.yaml and fill in the three `TODO`s.

  1. TODO 1: run three copies (replace replicas: 1):

    replicas: 3

  2. TODO 2: the image you just built (replace image: REPLACE_ME):

    image: evergreen-quote-api:1.0

  3. TODO 3: the container’s port (replace the containerPort: 0 line):

    - containerPort: 3000

  4. Save the file.

Notice two things that were already there:

  • resources: requests (what the pod is guaranteed) and limits (its ceiling). This is how the scheduler packs pods onto nodes and stops one pod from starving others.

  • readinessProbe: Kubernetes checks / on port 3000 before sending traffic to a pod, so users never hit a container that is still starting.

 Note

The :1.0 on the image is doing quiet work. When an image tag is a real version, Kubernetes uses a local copy if it has one, which is what makes kind load work. Tag an image latest and Kubernetes goes looking for it in a registry every time, so the same manifest would fail on your local cluster. "Never deploy latest`" is standard advice for this reason and for a bigger one: `latest does not tell you what is actually running.

Why this matters: replicas: 3 is the entire high-availability story in one line: three copies across the cluster, so one failure never takes the service down. Changing that number up or down is scaling.

1.11. Complete the Service

Open k8s/service.yaml and fill in the three `TODO`s.

  1. TODO 4: ask for an external address (replace type: ClusterIP):

    type: LoadBalancer

  2. TODO 5: send traffic to pods with the matching label (replace app: REPLACE_ME):

    selector:
  app: evergreen-quote-api

  3. TODO 6: forward to the container’s port (replace targetPort: 0):

    targetPort: 3000

  4. Save the file.

Why this matters: The selector is the glue: the Service finds every pod labeled app: evergreen-quote-api (all three replicas) and balances traffic across them. Add more replicas and they join the pool automatically. This label-based wiring is everywhere in Kubernetes, and a selector that matches nothing is the most common reason a healthy app is unreachable.

1.12. Deploy to the Local Cluster

  1. Confirm you are still pointed at the local cluster, not the one AWS is building:

    kubectl config current-context

    It must print kind-evergreen. If it does not, run kubectl config use-context kind-evergreen.

  2. Check your YAML with a dry run before applying it for real:

    kubectl apply --dry-run=client -f k8s/

    You should see both objects validated:

    deployment.apps/evergreen-quote-api created (dry run)
service/evergreen-quote-api created (dry run)

    If you see an error instead, read the line it points to: broken indentation or a misspelled field name is the usual cause.

     Note

    Be clear about what this dry run proves. It checks shape: YAML syntax, field names, and types. It does not judge values: a leftover REPLACE_ME or a 0 port sails straight through, because they are structurally valid. Real pipelines add policy checks on top of kubectl for exactly this reason.

  3. Apply the manifests for real and watch the pods appear:

    kubectl apply -f k8s/
kubectl get pods

    You should see three evergreen-quote-api pods, each named after the Deployment plus a random suffix, reaching Running within seconds. If a pod sits in ErrImagePull or ImagePullBackOff, the kind load step did not run or the image tag in the Deployment does not match what you built.

    Figure 1. Desired state, reconciled: you asked for three replicas and three pods appeared

Why this matters: Checking which cluster you are pointed at before you apply anything is a habit, not a formality. One kubectl command reaches whichever cluster the current context names, and the command gives you no other hint. Applying to the wrong cluster is a well-known way for a routine change to land somewhere it should not.

1.13. Watch Self-Healing and Scaling

  1. Delete one pod and watch Kubernetes replace it. Copy a pod name from the previous listing:

    kubectl delete pod <one-pod-name>
kubectl get pods

    A new pod, with a fresh random suffix, is already ContainerCreating while the old one still shows Terminating. You never asked for it; the Deployment did its job. The old name lingers in the list for up to 30 seconds, because Kubernetes gives a stopping pod that long to finish work already in flight before it forces the container to stop.

  2. Scale to five with one command:

    kubectl scale deployment/evergreen-quote-api --replicas=5
kubectl get deployment evergreen-quote-api

    Two new pods join the original three, and the Deployment reports 5/5 ready.

  3. Scale back down to three:

    kubectl scale deployment/evergreen-quote-api --replicas=3

Why this matters: You deleted a running pod and the platform fixed it for you. That is self-healing, and it is why teams sleep at night. Scaling from three to five was one command, with no new servers to provision by hand.

1.14. Reach the API on the Local Cluster

  1. Look at the Service you created:

    kubectl get svc evergreen-quote-api

    The EXTERNAL-IP column reads <pending>, and it stays that way:

    NAME                  TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
evergreen-quote-api   LoadBalancer   10.96.209.101   <pending>     80:30427/TCP   25s

    That is not a failure. You asked for a load balancer, and there is no cloud here to provision one from. Kubernetes will keep waiting for a provider that never arrives.

  2. Before reaching for the pods, confirm the Service actually found them. This is the one mistake a dry run cannot catch:

    kubectl describe svc evergreen-quote-api | grep -E 'Selector|Endpoints'

    You should see your selector and three pod addresses behind it:

    Selector:                 app=evergreen-quote-api
Endpoints:                10.244.0.3:3000,10.244.0.6:3000,10.244.0.5:3000

    An empty Endpoints: line means the Service is wired to nothing. Either the label in TODO 5 does not match the Deployment’s app label exactly, or the pods are not Ready yet. Check kubectl get pods first, then the two labels.

  3. Reach the pods, by opening a tunnel from your VM into the cluster:

    kubectl port-forward svc/evergreen-quote-api 8080:80

    It prints Forwarding from 127.0.0.1:8080 → 3000 and stays running.

  4. Open a third terminal (Terminal → Split Terminal) and call the API:

    curl http://localhost:8080/api/quotes

    You get the familiar JSON array of four quotes, q1 through q4, served by one of your three pods.

  5. Press Ctrl+C in the port-forward terminal to close the tunnel.

Why this matters: <pending> is the honest answer to a question the local cluster cannot answer, and it is your first look at the line between portable Kubernetes and the platform underneath. The manifest is valid, the cluster understood it, and nothing is broken. The same file is about to behave differently, and you have not changed a character of it.

1.15. Push the Image to Amazon ECR

Check your second terminal. When eksctl finishes, it prints EKS cluster "evergreen-your-initials-1234" in "us-east-1" region is ready. If it is still working, let it finish before continuing.

Your cloud cluster has the same problem your local cluster had: it cannot see the image on your VM. This time the answer is a registry. Amazon ECR is the AWS container registry.

  1. In your first terminal, set three values you use for the rest of the lab, substituting your own name:

    export ACCOUNT_ID=$(aws sts get-caller-identity --query Account --output text)
export REPO=evergreen-quote-api-your-initials-1234
export IMAGE=$ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com/$REPO:1.0
echo $IMAGE

    echo prints the full image address, something like 123456789012.dkr.ecr.us-east-1.amazonaws.com/evergreen-quote-api-ae-2431:1.0. That address is where the image will live.

     Note

    These values live only in this terminal. If you open a new one later, run the three export lines again before using $IMAGE.

  2. Create the repository:

    aws ecr create-repository --repository-name $REPO --region us-east-1

  3. Let Docker sign in to it:

    aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin $ACCOUNT_ID.dkr.ecr.us-east-1.amazonaws.com

    You should see Login Succeeded.

  4. Give your image its second name and push it:

    docker tag evergreen-quote-api:1.0 $IMAGE
docker push $IMAGE

    Watch the layers upload. The Node runtime layers are the large ones; your application code is a few kilobytes on top.

  5. Confirm it arrived:

    aws ecr describe-images --repository-name $REPO --region us-east-1

Why this matters: docker tag did not copy anything or build anything. It gave the same image a second name, and that name says where the image belongs. This is the whole mechanism behind "promote the build": one image, built and tested once, referred to by a new address as it moves toward production. Nothing is rebuilt, so nothing can differ between what you tested and what you ship.

1.16. Deploy the Same Manifests to EKS

  1. Point kubectl at your EKS cluster, substituting your cluster name:

    aws eks update-kubeconfig --region us-east-1 --name evergreen-your-initials-1234

  2. Confirm the switch, and confirm the cluster is real:

    kubectl config current-context
kubectl get nodes

    The context is now a long ARN ending in your cluster name, and two EC2 nodes show Ready. Your local cluster is untouched; you are simply pointed somewhere else.

  3. Change the one line that has to change. Update the Deployment to pull from ECR instead of expecting a local image:

    sed -i "s|image: evergreen-quote-api:1.0|image: $IMAGE|" k8s/deployment.yaml

  4. Open k8s/deployment.yaml in VS Code and look at what changed. The image: line now carries the full ECR address. Every other line in both files is exactly what you wrote for the local cluster.

    If the line still reads evergreen-quote-api:1.0, the value you put in TODO 2 differs from the one the command looked for. Edit the line by hand so it matches the address echo $IMAGE printed.

  5. Apply the manifests:

    kubectl apply -f k8s/
kubectl get pods

    Three pods start again, this time on AWS virtual machines, pulling your image from ECR.

  6. Watch the Service get what it asked for:

    kubectl get svc evergreen-quote-api

    Run it again after a minute or two. The EXTERNAL-IP column changes from <pending> to an AWS load balancer address ending in .us-east-1.elb.amazonaws.com. This takes two to three minutes.

Why this matters: type: LoadBalancer was a request all along. On the local cluster, nothing was listening. On EKS, the cluster reads that same line, calls the AWS API on your behalf, and a real load balancer appears with a public address. You did not write any AWS-specific configuration to make that happen.

1.17. Call the API on the Public Internet

  1. Capture the address and call the API (wait a few minutes and try again if it fails):

    export API_URL=$(kubectl get svc evergreen-quote-api \
  -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
echo $API_URL
curl http://$API_URL/api/quotes

    You get the same four quotes, this time from a cluster in an AWS data center, through a load balancer, spread across three pods.

     Note

    If curl fails on the first try, wait a minute and run it again. The address exists before the load balancer has finished registering the pods behind it as healthy.

    Figure 2. The same manifests, now on AWS: a real load balancer address answering with the Evergreen quotes

  2. Open the URL in Chrome, adding the path: http://<your-address>/api/quotes. The quotes load in the browser.

  3. Try self-healing once more, here on the cloud cluster:

    kubectl get pods
kubectl delete pod <one-pod-name>
kubectl get pods

    The replacement appears exactly as it did locally. The behavior is a property of Kubernetes, not of the cloud you run it on.

Why this matters: You ran the same application on a laptop-sized cluster and on a managed cloud cluster using one set of files, and the only edit was where to fetch the image. That is what people mean when they say Kubernetes is portable, and it is the strongest argument for adopting it.

  • The Pod / Deployment / Service concepts you used are portable: they work on any Kubernetes, anywhere. Five of the six values you filled in were identical on both clusters.

1.19. Clean Up

The order here matters. Delete the Kubernetes objects first, then the cluster.

  1. Delete the Deployment and Service from EKS:

    kubectl delete -f k8s/

     Important

    Deleting the Service is what releases the AWS load balancer. Skip this step and the load balancer keeps running and keeps charging, and eksctl fails to delete the cluster’s network because the load balancer is still attached to it. "Delete the workload, then the cluster" is the rule.

  2. Switch to your second terminal, the one that created the cluster, and delete it there, substituting your cluster name:

    eksctl delete cluster --name evergreen-your-initials-1234 --region us-east-1

    This takes 10 to 15 minutes and needs no attention. Let it run and finish the remaining steps back in your first terminal, which still holds your $REPO value.

  3. Delete the ECR repository and the image in it:

    aws ecr delete-repository --repository-name $REPO --region us-east-1 --force

  4. Delete the local cluster:

    kind delete cluster --name evergreen

  5. When eksctl finishes, confirm nothing is left:

    eksctl get cluster --region us-east-1

Why this matters: Cloud resources keep costing money and keep being reachable until somebody removes them, and a half-deleted cluster is worse than either state: the expensive parts survive, and the tool that could have removed them now reports an error. "Who cleans this up, and when?" belongs in every deployment conversation.
