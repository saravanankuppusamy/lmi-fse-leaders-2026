WA3863 Lab Guide

Cloud Platform Deployment using AWS EC2, S3 Bucket and AWS Lambda for Leaders

Evergreen Insurance: Deploying the Site to the AWS Cloud

Lab 1

In this lab, you will deploy the Evergreen site to AWS. You will run the site locally to prove the artifact works, create an S3 bucket, make it serve a public website, read the permissions that guard it, and complete and run the deploy script. At the end, you will have a live URL that anyone on the internet can open.

The site you are deploying is the Evergreen quote page itself, the front end this program has built up since Phase 1; the back-end service you finished in Week 5 gets its own journey to the cloud in the next two weeks, first containerized, then orchestrated.

You are not expected to become a cloud engineer. This lab deliberately keeps the moving parts to a minimum: one storage service, one permission decision, one short script. No CDN, no servers, no build pipeline. The point is that "deploying to the cloud" stops being abstract, because you have done it.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

"Push it to S3," "the bucket is public," "that needs an IAM policy," "use least privilege": these phrases shape every cloud deployment and every cloud cost and security review. After this lab they will be concrete steps you have followed, not cloud jargon.

1.3. What You Need

  • An AWS account you can sign in to, with permission to create an S3 bucket. Your instructor provides the sign-in details.

  • AWS CLI credentials for that account (an access key ID and secret access key), or an already-configured CLI on your VM.

 Note

Everything in this lab fits inside the AWS Free Tier, and the final step deletes the bucket. Follow the cleanup section so nothing is left running.

1.4. What’s Already Set Up on Your Lab VM

  • VS Code, a terminal, and Python 3 (to serve the site locally).

  • The AWS CLI, for talking to AWS from the terminal.

  • The starter project: the Evergreen site/ (the files you deploy) and a deploy/ folder with the deploy script, two policy files, and an architecture document.

1.5. Open the Project

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-cloud-deploy in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-cloud-deploy.

1.6. The Deployment at a Glance

The lab walks the same path a real release does, in seven moves:

  1. Prove the artifact works: serve site/ locally and click around.

  2. Read the architecture (deploy/infrastructure.md): browser → S3, and why.

  3. Create the bucket and turn on static website hosting.

  4. Grant read access with a bucket policy, and read the deploy policy that limits what the deployer may touch.

  5. Complete the script (deploy/deploy-to-s3.sh, TODO 1 and TODO 2).

  6. Run the deploy and open the live site.

  7. Change something, redeploy, then clean up.

Think of it as shipping a package: check the contents, choose the warehouse, decide who may open the box and who may restock it, write the two-line dispatch note, then send it.

 Tip

The two snippets in the script section replace the numbered TODO comment blocks in deploy/deploy-to-s3.sh; each TODO comment already names the exact command it expects, so the script is self-checking. Everything else in this lab is reading, clicking, and running, not writing.

1.7. Run the Deployable Artifact Locally

Before deploying anything, confirm the thing you are shipping actually works.

  1. Serve the site from the integrated terminal:

    cd site
python3 -m http.server 8080

    The terminal prints Serving HTTP on 0.0.0.0 port 8080 …​ and keeps running.

  2. Open http://localhost:8080 in Chrome. The Evergreen quote page loads: the estimate reads $400.00 for the default inputs, and the "Recent quotes" panel lists four quotes loaded from quotes.json.

    Figure 1. The artifact, proven before shipping: the same files you are about to deploy, served from your own machine

  3. Go back to the terminal and press Ctrl+C to stop the server, then return to the lab root:

    cd ..

Why this matters: Deployment ships exactly these files. There is no build step for a static site: what you tested locally is what goes to the cloud. "Test the artifact, then ship the artifact" is the whole game.

1.8. Understand the Architecture

  1. Open deploy/infrastructure.md and read it.

  2. The shape you are building is: browser → S3 (the files). Two reasons this beats a virtual server for a static site:

    • S3 stores the files cheaply and durably, with no server to patch and nothing to scale by hand.

    • S3 static website hosting turns the bucket into a web server for those files, for a few cents a month.

  3. Note what this shape does not have: a content delivery network. In production, teams put CloudFront (AWS’s CDN) in front of the bucket to add HTTPS, a custom domain, and caching at edge locations near the user. That is one more service to configure and one more cache to invalidate, so it is out of scope today; your site will be served over plain http.

Why this matters: Choosing S3 over an EC2 virtual server is a real architecture decision: cost, scale, and maintenance all improve for static content. Knowing why lets you weigh similar trade-offs your teams bring you.

1.9. Create the S3 Bucket

  1. In Chrome, open the AWS Console and sign in with the account details your instructor provides.

  2. In the search bar at the top, type S3 and open the S3 service.

  3. Click Create bucket.

  4. Set the bucket name. The bucket name has to be all lowercase letters, numbers, and hyphens. Bucket names are globally unique across all of AWS, so add something of your own:

    evergreen-quote-site-your-initials-1234

    For example, evergreen-quote-site-ae-2431. Use lowercase letters, numbers, and hyphens only.

  5. Set Region to US East (N. Virginia) us-east-1.

  6. Under Block Public Access settings for this bucket, clear the Block all public access checkbox, then select the acknowledgment checkbox that appears.

  7. Leave every other setting at its default and click Create bucket.

  8. Write your bucket name down. You need it three more times in this lab.

 Caution

Turning off Block Public Access is a deliberate decision, not a default to click past. It is correct for a public marketing site whose whole job is to be read by strangers. It is wrong for anything holding customer data, and a bucket made public by accident is one of the most common cloud data leaks. Ask which kind of bucket you are looking at.

1.10. Turn On Static Website Hosting

  1. If not already there, navigate to the bucket list, click your bucket name to open it.

  2. Go to the Properties tab and scroll to the bottom, to Static website hosting. Click Edit.

  3. Configure it:

    • Static website hosting: Enable

    • Hosting type: Host a static website

    • Index document: index.html

    • Error document: index.html

  4. Click Save changes.

  5. Scroll back to Static website hosting and copy the Bucket website endpoint. It looks like this:

    http://evergreen-quote-site-ae-2431.s3-website-us-east-1.amazonaws.com

  6. Open that URL in a new tab. You get 403 Forbidden. That is expected: the bucket is empty, and nobody has been granted permission to read it yet.

Why this matters: "The bucket exists" and "the site is live" are two different things. The next two steps are the gap between them: permission to read, and files to read.

1.11. Grant Read Access with a Bucket Policy

  1. In VS Code, open deploy/bucket-policy.json. It grants one action, s3:GetObject, to everyone, on the objects inside one bucket.

  2. Replace BUCKET-NAME with your bucket name, then save the file. The /* on the end must stay: the policy applies to the objects in the bucket, not the bucket itself.

  3. Copy the whole file contents.

  4. In the AWS Console, on your bucket, go to the Permissions tab.

  5. Under Bucket policy, click Edit, paste the policy, and click Save changes.

  6. Reload the website endpoint tab. You now get 404 Not Found instead of 403 Forbidden. The permission is in place; the files are not there yet.

Why this matters: A bucket policy answers "who may read this?" It is public here on purpose, and it grants exactly one action on exactly one bucket. "Public" is not one switch; it is a policy you can read line by line and ask questions about.

1.12. Read the Least-Privilege Deploy Policy

The bucket policy governs the readers. A second policy governs the writer.

  1. Open deploy/iam-policy.json. This is the permission set for whatever runs the deployment: a CI pipeline, or an engineer’s role.

  2. Notice how narrow it is:

    • It can upload to, delete from, and list one bucket, and nothing else.

    • It cannot read other buckets, launch servers, or touch anything else in the account.

  3. You are not applying this policy today; your lab credentials are broader so the lab stays short. In production, the deploy pipeline gets exactly this and no more.

Why this matters: This is the principle of least privilege. If these credentials leaked, the blast radius is one website, not the whole account. "Why does this role have so many permissions?" is one of the most valuable questions a leader can ask in a security review.

1.13. Connect the AWS CLI to Your Account

  1. In the VS Code terminal, from the lab root, check whether the CLI already has credentials:

    aws sts get-caller-identity

    If it prints an account number and an ARN, you are connected. Skip to the next section.

  2. If it reports missing credentials, configure them:

    aws configure

    Enter the AWS Access Key ID and Secret Access Key your instructor provides, us-east-1 for the default region, and json for the output format.

  3. Run aws sts get-caller-identity again to confirm it works.

Why this matters: This is the moment a script becomes able to change your cloud account. Whoever holds these credentials holds whatever the attached policy allows, which is why the previous section matters so much.

1.14. Complete the Deployment Script

  1. Open deploy/deploy-to-s3.sh. At the top, set BUCKET to the bucket you created:

    BUCKET="evergreen-quote-site-YOUR-INITIALS-1234"

  2. Fill in TODO 1 (upload):

    aws s3 sync "$SITE_DIR" "s3://$BUCKET" --delete

  3. Fill in TODO 2 (verify what landed in the bucket):

    aws s3 ls "s3://$BUCKET" --recursive --human-readable

  4. Save the file, then let bash check your work from the lab root:

    bash -n deploy/deploy-to-s3.sh

    No output means no syntax errors; a line number in the output points at a typo to fix.

  5. Read the finished script top to bottom; it is the entire deployment: upload the files, then confirm what is there.

Why this matters: Two commands. s3 sync uploads only what changed, and --delete removes files that no longer exist locally, so the bucket ends up matching your folder exactly. A deploy that also checks itself is the difference between "the script ran" and "the site is right."

1.15. Deploy for Real

  1. Run the script from the lab root:

    bash deploy/deploy-to-s3.sh

  2. Watch the output. You should see four upload: lines (index.html, styles.css, app.js, quotes.json), then the listing from TODO 2, then the site URL.

  3. If the script stops with an error, read the message before rerunning:

    • Unable to locate credentials: rerun aws configure.

    • NoSuchBucket or AccessDenied: the BUCKET value in the script doesn’t match the bucket you created, or the bucket is in a different region.

    • Permission denied: you ran ./deploy/deploy-to-s3.sh instead of bash deploy/deploy-to-s3.sh. The starter files arrive without the executable bit set, so run them through bash, or run chmod +x deploy/deploy-to-s3.sh once and then either form works.

1.16. See the Site Live

  1. Reload the bucket website endpoint tab. The Evergreen quote page loads from AWS.

  2. Use it: change the coverage amount, click Get my quote, and confirm the estimate updates and the "Recent quotes" panel fills in. This is the same artifact you ran on localhost, now served to the internet.

  3. Look at the address bar: the URL is http, not https, and there is no padlock. Adding HTTPS and a real domain name is exactly the job CloudFront does in the production version of this architecture.

Why this matters: A deployment is not magic; it is a short, reviewable script and a few configuration decisions. When you can read them, you can ask the right questions: what does it touch, what permissions does it need, and what happens if it fails halfway.

1.17. Change Something and Redeploy

  1. In VS Code, open site/index.html and change the headline on line 21:

    <h1>Coverage that grows with you (v2)</h1>

  2. Save the file and redeploy:

    bash deploy/deploy-to-s3.sh

    Only index.html uploads this time. s3 sync skips the three files that did not change.

  3. Reload the site in Chrome. The new headline appears immediately.

 Note

It appears immediately because nothing is caching it. Add CloudFront to this architecture and this step gets a companion: a cache invalidation to tell the edge locations to refetch. Forgetting it is the source of countless "I deployed but nothing changed" tickets.

1.18. Clean Up

Leaving a public bucket behind is both a cost and a security loose end. Delete it now.

  1. Empty and delete the bucket from the terminal, using your bucket name:

    aws s3 rm "s3://YOUR-BUCKET-NAME" --recursive
aws s3 rb "s3://YOUR-BUCKET-NAME"

  2. Reload the website endpoint tab. It no longer serves the site.

Why this matters: Cloud resources keep costing money and keep being reachable until somebody removes them. "Who cleans this up, and when?" belongs in every deployment conversation.

1.19. Review

In this lab you:

  • Ran the deployable artifact locally to confirm it works before shipping.

  • Created an S3 bucket and turned on static website hosting.

  • Made a deliberate public access decision and wrote it down as a bucket policy.

  • Read a least-privilege deploy policy and saw how it limits the blast radius.

  • Completed and ran the deployment script: s3 sync plus a verification listing.

  • Deployed a real site, changed it, redeployed, and cleaned it up.

You took the Evergreen site from a local folder to a public URL on AWS, and you can now reason about cloud deployments, costs, and the security policies that guard them. Next week, the Evergreen API gets the same treatment a different way: packed into a Docker container.
