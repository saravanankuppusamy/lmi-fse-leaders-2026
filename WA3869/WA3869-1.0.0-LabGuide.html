Evergreen Insurance Quote Data: Storing and Querying in MongoDB

Lab 1

In this lab, you will move the Evergreen quote data into a real NoSQL database, MongoDB, and query it with the MongoDB shell, mongosh. Until now the quotes lived in memory and vanished when the server stopped; you saw exactly that in Week 3, when a server restart reset the list. Now they live as documents in a database, the way real data does.

This is Week 4 of Phase 3. The lab is pure database work, on purpose: no API in front, just you and the data. Next week you wire the Week 2 Express API to this very database, and the two halves meet.

You are not expected to become a database administrator. You are here to see what a document database is, how it differs from the spreadsheet-like tables many people picture, and what your engineers mean by "a collection," "a document," "a query filter," and "an index."

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

"Store it as a document," "add an index or that query will be slow," "run an aggregation": these are everyday data conversations. After this lab, each one will be something you have done by hand, so you can follow a data-modeling discussion and ask informed questions.

1.3. What’s Already Set Up on Your Lab VM

  • MongoDB is installed and running as a background service; there is nothing to start.

  • mongosh, the MongoDB shell, is available in the terminal.

  • The lab folder has seed.js (sample quote documents).

1.4. The Lab at a Glance

You will work through six moves, each one a database idea your engineers use daily:

  1. Load and look: seed six quote documents, then find() them all.

  2. Filter: pick out documents by field and by comparison ($gte).

  3. Project: return only the fields you need.

  4. Update: change a field with $set, grow an array with $push.

  5. Aggregate: roll the quotes up by type with $group.

  6. Index: make a query fast and prove it with explain.

Think of the collection as a drawer of paper claim files: filtering is pulling the right folders, projecting is photocopying just one page from each, and the index is the alphabetical tab system that saves you reading every folder.

 Tip

Run each command at the mongosh prompt as the lab reaches it. Every step below states exactly what the shell should print, so you always know whether it worked.

1.5. Open the Project and Load the Data

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-mongodb-data in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-mongodb-data.

  4. Load the sample quotes into a database named evergreen:

    mongosh evergreen seed.js

    You should see Inserted 6 quotes into the 'quotes' collection.

  5. Open an interactive shell on that database:

    mongosh evergreen

    Your prompt changes to evergreen>. You are now "inside" the database.

     Note

    seed.js starts by dropping the collection, so you can re-run mongosh evergreen seed.js at any point to reset the data to a clean six quotes.

1.6. Documents, Not Rows

  1. List everything in the collection:

    db.quotes.find()

    All six documents print, q1 through q6.

    Figure 1. Six documents, one collection: notice q5 carries two tags while its neighbors carry one

  2. Look at the output. Each document is a JSON-like record, and notice q5 has two tags while others have one. In a relational table every row has the same columns; here, documents in the same collection can vary.

Why this matters: This is the core mental shift. MongoDB stores flexible documents, not rigid rows. The hierarchy is Database → Collection → Document, mirroring Database → Table → Row, but the document can hold nested data (like the tags array) directly.

1.7. Filter (the WHERE of NoSQL)

  1. Find only the auto quotes:

    db.quotes.find({ type: "auto" })

    Three documents come back: q1, q4, and q6.

  2. Now find the more expensive quotes:

    db.quotes.find({ monthlyPremium: { $gte: 200 } })

    Two documents match: q2 (375) and q5 (248.4).

Why this matters: The object you pass to find() is the filter. $gte ("greater than or equal") is one of MongoDB’s comparison operators, the document-database version of WHERE monthlyPremium >= 200. When engineers say "the query filter," this is it.

1.8. Projection (asking for fewer fields)

  1. Show only the type and monthlyPremium of auto quotes:

    db.quotes.find({ type: "auto" }, { type: 1, monthlyPremium: 1 })

    Each of the three results now shows just _id, type, and monthlyPremium. (The _id field tags along by default; add _id: 0 to the projection if you want it gone.)

Why this matters: The second argument is a projection: 1 means "include this field." This is the same "ask only for what you need" idea you saw with GraphQL last week, now at the database layer. Smaller results mean faster queries and less data over the wire.

1.9. Update a Document

  1. Change quote `q4’s premium:

    db.quotes.updateOne({ _id: "q4" }, { $set: { monthlyPremium: 110.5 } })

    The response shows modifiedCount: 1.

  2. Add a tag to quote q1:

    db.quotes.updateOne({ _id: "q1" }, { $push: { tags: "reviewed" } })

    Again modifiedCount: 1.

  3. Confirm: db.quotes.find({ _id: "q1" }) shows q1 with tags: [ 'renewal', 'reviewed' ].

Why this matters: updateOne takes a filter (which document) and an update (what to change). $set replaces a field; $push adds to an array. Updating by the unique _id is safer than matching by a value that might repeat, a habit worth recognizing in reviews.

1.10. Aggregate (summarize the data)

  1. Count the quotes of each type and their average premium:

    db.quotes.aggregate([
  { $group: {
      _id: "$type",
      count: { $sum: 1 },
      avgPremium: { $avg: "$monthlyPremium" }
  } }
])

  2. You get one result per coverage type (the order may vary): auto with count: 3, home with count: 2, life with count: 1, each with its average premium. The auto average reflects the update you just made to q4.

Why this matters: An aggregation pipeline transforms data in stages; here, $group rolls the documents up by type. This is how dashboards and reports are built straight from the database. When an engineer says "we’ll do that in an aggregation," this is the tool.

1.11. Index for Speed

  1. Without an index, MongoDB checks every document. Create an index on type:

    db.quotes.createIndex({ type: 1 })

    The shell answers with the new index’s name: type_1.

  2. See whether a query now uses it:

    db.quotes.find({ type: "auto" }).explain("executionStats")

    In the output, look for "stage": "IXSCAN" (an index scan: good) rather than "COLLSCAN" (a full collection scan).

    Figure 2. The proof: after createIndex, the winning plan reads IXSCAN instead of COLLSCAN

Why this matters: Indexes are why a query stays fast as data grows from six documents to six million. "Add an index" is one of the most common performance fixes your engineers make, and now you have seen exactly what it does.

1.12. Review

In this lab you:

  • Loaded data as documents into a MongoDB collection and saw flexible schema firsthand.

  • Filtered documents with query operators like $gte (the NoSQL WHERE).

  • Used a projection to return only the fields you needed.

  • Updated documents with $set and $push, matching on the unique _id.

  • Summarized data with an aggregation pipeline ($group).

  • Created an index and confirmed a query used it via explain.

You gave the Evergreen quotes a real home in a document database, and you now understand, firsthand, the vocabulary behind nearly every NoSQL data conversation. Next week, the Week 2 Express API connects to this database, and saved quotes finally survive a restart.
