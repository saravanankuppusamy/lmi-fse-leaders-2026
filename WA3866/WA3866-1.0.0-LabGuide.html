Evergreen Insurance Quote Page — Loading Data with useEffect

Lab 1

In this lab, you will teach the Evergreen React app to load its data from a server — the way real applications do. Back in Week 1 you fetched a list of quotes with plain JavaScript. Now you will do it the React way, using useEffect, and you will handle the three states every data fetch must handle: loading, error, and success.

You are not expected to master React’s effect system. You are here to see how a React app fetches data, why "loading" and "error" states matter, and what your engineers mean when they say "that runs in an effect."

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work — for example, Ctrl+` to open the integrated terminal — use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

Almost every screen your teams build loads data from somewhere. The difference between an app that feels solid and one that feels broken usually comes down to how it handles the waiting and the failure — the loading spinner and the friendly error. After this lab, "fetch it in a useEffect" and "handle the loading state" will be things you have done.

  • The starter project: the Evergreen React app. The recent-quotes data lives in public/quotes.json, served by Vite at /quotes.json. The RecentQuotes component has the state set up and TODO comments for the fetch.

1.5. Understand the Three States

  1. Open src/components/RecentQuotes.tsx. Notice the three pieces of state already declared:

    const [quotes, setQuotes] = useState<Quote[]>([]);
const [loading, setLoading] = useState(true);
const [error, setError] = useState<string | null>(null);

Why this matters: Every data fetch is really three situations on screen: we’re waiting (loading), it failed (error), and here’s the data (success). Apps that forget the first two are the ones that show blank screens and spinners that never stop. Tracking all three is the habit that separates polished apps from frustrating ones.

1.6. Fetch in a useEffect

A useEffect runs code after React renders — the right place for a side effect like a network request.

  1. Fill in TODO 1, TODO 2, and TODO 3 so the effect fetches the quotes on mount:

    useEffect(() => {
  const controller = new AbortController();

  async function loadQuotes() {
    try {
      setLoading(true);
      setError(null);
      const res = await fetch("/quotes.json", { signal: controller.signal });
      if (!res.ok) throw new Error(`HTTP ${res.status}`);
      const data: Quote[] = await res.json();
      setQuotes(data);
    } catch (err) {
      if (err instanceof Error && err.name !== "AbortError") {
        setError("Could not load recent quotes.");
      }
    } finally {
      setLoading(false);
    }
  }

  loadQuotes();
  return () => controller.abort(); // cleanup: cancel if unmounted
}, []);

Two important details:

  • The empty dependency array [] means "run this once, when the component first appears." A different value there would re-run the effect when that value changes.

  • The cleanup function (the return () ⇒ …​) cancels the request if the component disappears before the data arrives. React calls it automatically. This is why your engineers talk about "cleaning up effects."

1.7. Show Each State on Screen

The starter <aside> keeps its <h2>Recent quotes</h2>, but it also ends with a plain <ul className="recent-list">…</ul> that always renders. You will replace the three TODO comments and that leftover <ul> so the panel shows the right thing for each state — leaving the surrounding <aside className="recent-quotes"> and its <h2> exactly where they are.

  1. Replace TODO 4, TODO 5, and TODO 6 together with the existing <ul className="recent-list">…</ul> block directly below them with:

    {loading && <p className="loading">Loading recent quotes…</p>}
{error && <p className="message">{error}</p>}
{!loading && !error && (
  <ul className="recent-list">
    {quotes.map((quote) => (
      <li key={quote.id}>
        <span className="quote-type">{quote.type}</span> &mdash;{" "}
        <span className="quote-premium">
          {formatCurrency(quote.monthlyPremium)}/mo
        </span>
      </li>
    ))}
  </ul>
)}

    The quote list now lives inside the {!loading && !error && (…)} condition, so there is exactly one <ul> — and you have not pasted another <aside> or <h2>.

     Caution

    Don’t paste the <aside> or the <h2> again, and don’t leave the starter’s original <ul className="recent-list"> in place. If the recent quotes show up twice — once in the panel and again, unstyled, below it — either the old <ul> is still there or a second <aside> was pasted inside the first. Remove the leftover so the list appears once.

  2. Save and switch to the browser. You may briefly see "Loading recent quotes…", then the list of five quotes appears.

    Figure 1. The success state: the Recent quotes panel renders all five quotes in a single styled card

Why this matters: The UI now tells the truth at every moment — waiting, then loaded. That brief "Loading…" is not clutter; it is the app being honest about what is happening.

1.8. See the Error State

  1. In the Explorer, rename public/quotes.json to public/quotes-DOWN.json (right-click → Rename) to simulate the data service being unavailable.

  2. Save and reload the page. The panel now shows "Could not load recent quotes." — not a blank box, not a stuck spinner.

  3. Rename the file back to public/quotes.json. The list returns.

Why this matters: This is the answer to the question: "what does the user see when the backend is down?" A well-built screen degrades to a clear message. You just built that behavior on purpose.

1.9. Notice the Double Fetch

  1. Open the DevTools Network tab and reload. In development, React’s Strict Mode intentionally runs effects twice to help you catch missing cleanup — you may see two requests for quotes.json.

    Figure 2. Strict Mode double-invokes the effect: the first quotes.json request is canceled by the cleanup, the second returns 200

  2. This does not happen in the production build. It is a development-only check that rewards the AbortController cleanup you added to the effect.

Why this matters: When an engineer says "that’s just Strict Mode double-invoking in dev," this is what they mean — and the cleanup you added is exactly what makes that safe.

1.10. Review

In this lab you:

  • Loaded data from a server with useEffect and an empty dependency array.

  • Tracked the three states of every fetch — loading, error, and success.

  • Cancelled the request on unmount with an AbortController cleanup function.

  • Built a real error state and proved it by simulating a backend outage.

You gave the Evergreen app the data-loading behavior real applications need — and you now understand, firsthand, why "handle the loading and error states" is such a common and important review comment.
