Express-Database Integration for Leaders

Evergreen Insurance Quote API: Connecting Express to MongoDB

Lab 1

In this lab, you will connect the Evergreen Quote API to a real MongoDB database using Mongoose. The API you built in Week 2 kept its quotes in memory; they vanished every time the server restarted. After this lab, the quotes are stored permanently in the database you met in Week 4, and the API validates every quote against a schema before saving it.

This is Week 5 of Phase 3, the week the two halves of the back end meet. The remaining weeks deploy, containerize, and orchestrate the service you finish today.

You are not expected to become a back-end developer. You are here to see how an application connects to a database, what a "model" and a "schema" are, and how validation protects the data your business relies on.

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

"Define the model," "the schema validation rejected it," "we persist that to Mongo": these are everyday full-stack review comments. After wiring an API to a database yourself, each one becomes concrete. You will also see the moment data becomes durable, the difference between a demo and a real system.

1.3. What’s Already Set Up on Your Lab VM

  • VS Code, Node.js, and a running MongoDB.

  • The starter project: an Express server wired to connect to MongoDB, a Quote model with a TODO schema, route handlers with TODO database calls, and a seed script.

1.4. Open the Project and Run It

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-express-mongodb in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-express-mongodb.

  4. In that same terminal, install the dependencies:

    npm install

  5. Open src/db.js. Notice it connects to mongodb://127.0.0.1:27017/evergreen, the same MongoDB (and the same database name) you queried with mongosh last week. The server calls this before it starts listening: an app should not accept requests it can’t fulfill.

1.5. The Integration at a Glance

You will make four changes, in this order:

  1. Define the schema (src/Quote.js, TODO 1): the contract every quote document must satisfy.

  2. Seed the database (npm run seed): load three starter quotes through that contract.

  3. Read from the database (TODO 2 and TODO 3): replace in-memory reads with find and findById.

  4. Write through the model (TODO 4): create a quote, and then watch the schema reject bad ones.

Think of Mongoose as the underwriting desk between the API and the filing room: every document passes its checks on the way in, so the files you later pull out can be trusted.

 Tip

Every snippet below replaces a numbered TODO comment; the comment itself restates what the code must do, and the commented example lines under each TODO are the same code you are pasting. After each step, the lab states exactly what curl or the console should show.

1.6. Define the Quote Schema

A Mongoose schema is the contract for a document: which fields exist, their types, and their rules. Open src/Quote.js and fill in TODO 1:

const quoteSchema = new mongoose.Schema(
  {
    type: { type: String, required: true, enum: ["auto", "home", "life"] },
    age: { type: Number, required: true, min: 18, max: 100 },
    coverageAmount: { type: Number, required: true, min: 10000 },
    monthlyPremium: { type: Number, required: true },
  },
  { timestamps: true }
);

  1. Save the file.

What you just declared:

  • required: true: the field must be present.

  • enum: type must be one of the three allowed values.

  • min / max: numeric bounds, enforced automatically.

  • timestamps: true: Mongoose adds createdAt and updatedAt for you.

Why this matters: The schema is validation that lives with the data. The same rules you wrote on the front end and in the API now also guard the database itself, so bad data cannot get in, no matter which client sends it.

1.7. Seed the Database

  1. Load a few starter quotes:

    npm run seed

    You should see Connected to MongoDB: mongodb://127.0.0.1:27017/evergreen followed by Seeded 3 quotes. The script connected to MongoDB, cleared the collection, and inserted three documents through your model.

     Caution

    Complete TODO 1 before seeding. Mongoose only saves fields the schema declares, so with the schema still empty the seed writes three quotes with no data in them. If that happens, finish the schema and run npm run seed again; it clears the collection first, so re-running is always safe.

1.8. Read Quotes from the Database

  1. Open src/index.js. Fill in TODO 2 (the list route):

    const quotes = await Quote.find();
res.json(quotes);

  2. Fill in TODO 3 (one by id):

    const quote = await Quote.findById(req.params.id);
if (!quote) return res.status(404).json({ error: "Not found" });
res.json(quote);

  3. Start the server in watch mode:

    npm run dev

    You should see Connected to MongoDB: …​ and then Evergreen Quote API (MongoDB) on http://localhost:3000. Watch mode (node --watch) restarts the server automatically when you save a file, which pays off at the next TODO.

  4. Open a second terminal beside it (Terminal → Split Terminal, or Ctrl+Shift+5) and request the list:

    curl http://localhost:3000/api/quotes

    You get the three seeded quotes, each with a database _id (a 24-character hex string) and createdAt/updatedAt timestamps. This data survives a restart.

    Figure 1. Real database documents: every quote now carries a Mongo _id and timestamps

Why this matters: Quote.find() and Quote.findById() are the model talking to MongoDB for you. await is back: every database call is asynchronous, exactly like the network calls from Phase 2. The model turns "talk to the database" into a method call.

1.9. Create a Quote (with Validation)

  1. Fill in TODO 4 (the create route):

    const monthlyPremium = calculatePremium(type, Number(age), Number(coverageAmount));
const quote = await Quote.create({
  type,
  age: Number(age),
  coverageAmount: Number(coverageAmount),
  monthlyPremium,
});
res.status(201).json(quote);

  2. Save. The watch process restarts the server; the two startup lines print again in the first terminal. Then create a quote:

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"auto","age":35,"coverageAmount":50000}'

    You get back the saved quote with its new _id and, for these inputs, "monthlyPremium":400, status 201.

  3. Confirm it persisted:

    curl http://localhost:3000/api/quotes

    The list now has four quotes, yours at the end.

     Tip

    Want proof of durability? Press Ctrl+C in the server terminal, run npm run dev again, and repeat the curl. Four quotes, still there. That restart used to erase everything in Week 2.

1.10. Watch the Schema Reject Bad Data

  1. Send a quote with an impossible age:

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"auto","age":5,"coverageAmount":50000}'

    You get a 400 whose message reads Path 'age' (5) is less than minimum allowed value (18): the min: 18 rule on age stopped it. The bad quote was never saved.

  2. Try an invalid coverage type:

    curl -X POST http://localhost:3000/api/quote \
  -H "Content-Type: application/json" \
  -d '{"type":"boat","age":35,"coverageAmount":50000}'

    Another 400: the message says boat is not a valid enum value for path type.

    Figure 2. The system working, not breaking: two bad quotes stopped at the door with clear 400s

Why this matters: The schema is the last line of defense for your data’s integrity. The central error handler turns Mongoose’s ValidationError into a clean 400, so the client gets a useful message instead of a crash. "The schema rejected it" is exactly this, and it is a good thing.

1.11. Review

In this lab you:

  • Connected an Express API to MongoDB with Mongoose, connecting before listening.

  • Defined a schema with types, required, enum, and min/max rules.

  • Replaced in-memory data with real database calls: find, findById, create.

  • Saw data persist across restarts: the leap from demo to real system.

  • Watched schema validation reject bad input with a clean 400.

You turned the Evergreen API into a durable, validated, database-backed service, the shape of nearly every back end your teams run in production. The rest of Phase 3 takes this service to the cloud: deploying it, containerizing it, and orchestrating it.
