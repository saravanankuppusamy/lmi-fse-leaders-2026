Evergreen Insurance Quote API: Exploring REST and GraphQL

Lab 1

In this lab, you will explore the Evergreen Quote API in two styles side by side: classic REST and GraphQL. They serve the same quote data, but they let a client ask for that data very differently. By the end you will have run queries in both, felt the difference firsthand, and implemented a GraphQL mutation.

This is Week 3 of Phase 3, and the server is an old friend: it is the Express API you built in Week 2, now with a GraphQL endpoint mounted beside the REST routes. Next week the quote data moves into a real database; today is about how clients ask for it.

You are not expected to design APIs. You are here to see what your engineers mean by "the endpoint over-fetches," "ask for just the fields you need," or "that’s a mutation."

1.1. A Note About Keyboard Shortcuts

Your lab VM runs inside your browser, which can sometimes capture a keyboard shortcut before it reaches the VM. If a shortcut doesn’t work (for example, Ctrl+` to open the integrated terminal), use the menu alternative instead (Terminal → New Terminal). Every shortcut in this lab has a menu path.

1.2. Why You’re Doing This Lab

REST and GraphQL are two of the most common ways teams expose data. The choice between them, and complaints about over-fetching, extra round-trips, or rigid endpoints, comes up constantly in architecture conversations. After this lab, both styles will be things you have used, not buzzwords.

1.3. What’s Already Set Up on Your Lab VM

  • VS Code and Node.js.

  • The starter project: the Evergreen API server, now serving REST routes and a GraphQL endpoint with an in-browser explorer (GraphiQL). The createQuote mutation has a TODO.

1.4. Open the Project and Run It

  1. Launch VS Code from the lab VM’s applications menu (or the desktop shortcut).

  2. In VS Code, choose File → Open Folder, navigate to Labfiles/evergreen-quote-api-explorer in your home folder, and click Open.

  3. Open the VS Code integrated terminal via Terminal → New Terminal (or press Ctrl+` ). Confirm you are in the lab folder:

    pwd

    You should see a path ending in Labfiles/evergreen-quote-api-explorer.

  4. In that same terminal, install the dependencies and start the server in watch mode:

    npm install
npm run dev

    You should see two lines: Evergreen API + GraphQL on http://localhost:3000 and GraphiQL explorer: http://localhost:3000/.

  5. Open http://localhost:3000/ in Chrome. This is GraphiQL, an interactive GraphQL explorer (the server ships a GraphiQL distribution called Ruru, so that name appears in the corner). Keep it open; you will spend most of the lab here.

     Note

    Leave the server running in its terminal for the whole lab. npm run dev uses node --watch, so when you edit the mutation later, the server restarts on save by itself. For the REST curl commands, open a second terminal beside it: Terminal → Split Terminal (or Ctrl+Shift+5).

1.5. The Lab at a Glance

You will make five small moves, each one a complete idea:

  1. Fetch everything over REST (curl): see the fixed, full-shape response.

  2. Ask for two fields in GraphQL: the same data, but you choose the shape.

  3. Add a field and query by id: feel how the client, not the server, evolves the response.

  4. Implement the createQuote mutation (TODO 1 in src/index.js): the one code change in this lab.

  5. Run the mutation: write data and read back chosen fields in a single call.

Think of REST as a fixed-menu restaurant (every order comes with everything) and GraphQL as ordering a la carte (you name exactly the dishes you want).

 Tip

The only snippet that changes a file is the mutation resolver, which replaces the numbered TODO 1 comment in src/index.js. Everything else is queries you paste into GraphiQL or curl commands you run in the second terminal, and after every step you should be able to point at the exact response described.

1.6. The REST Way: You Get Everything

  1. In the second terminal, request all quotes over REST:

    curl http://localhost:3000/api/quotes

  2. Look at the response: every quote comes back with all of its fields (id, type, age, coverageAmount, monthlyPremium), whether you needed them or not. It is the same JSON array of four quotes, q1 through q4, that this API returned in Week 2.

Why this matters: A REST endpoint returns a fixed shape. If your screen only needs the type and the premium, you still download everything else. That is over-fetching, a common reason teams look at GraphQL.

1.7. The GraphQL Way: You Ask for Exactly What You Need

  1. In GraphiQL (the browser), paste this query into the left pane and press the ▶ (Execute) button:

    query {
  quotes {
    type
    monthlyPremium
  }
}

  2. The response contains only type and monthlyPremium, nothing else. You asked for two fields; you got two fields: four quotes reading auto 96, home 375, life 84, auto 100.8.

    Figure 1. Two fields in, two fields out: the same four quotes, but only the shape you asked for

Why this matters: With GraphQL, the client decides the shape of the response. The same endpoint can serve a data-light mobile screen and a data-rich desktop screen without new endpoints. This is the headline GraphQL advantage: no over-fetching, no under-fetching.

1.8. Add a Field and Re-run

  1. Edit the query to also request age:

    query {
  quotes {
    type
    age
    monthlyPremium
  }
}

  2. Execute again. The new field appears in the response immediately, no server change required.

  3. Try a single quote by id:

    query {
  quote(id: "q1") {
    id
    type
    monthlyPremium
  }
}

    The response is a single object: {"data":{"quote":{"id":"q1","type":"auto","monthlyPremium":96}}}.

Why this matters: The schema is a typed contract. GraphiQL even autocompletes field names (try Ctrl+Space) because the API is self-documenting. When engineers call GraphQL "strongly typed and self-documenting," this is what they mean.

1.9. Implement the createQuote Mutation

Reads are only half the story. A mutation writes data.

  1. Open src/index.js and find the createQuote resolver (TODO 1). Replace the resolver (the TODO comment and the line that throws) with:

    createQuote: ({ type, age, coverageAmount }) => {
  const monthlyPremium = calculatePremium(type, age, coverageAmount);
  const newQuote = { id: randomUUID(), type, age, coverageAmount, monthlyPremium };
  quotes.push(newQuote);
  return newQuote;
},

  2. Save. In the server terminal, the watch process restarts the server automatically; the two startup lines print again. That restart is your cue that the new resolver is live.

     Note

    A restart also resets the in-memory quote list back to the original four quotes: there is no database yet. Next week you will meet the fix for exactly that.

1.10. Run the Mutation

  1. In GraphiQL, run a mutation that creates a quote and asks for specific fields back in the same call:

    mutation {
  createQuote(type: "home", age: 45, coverageAmount: 200000) {
    id
    type
    monthlyPremium
  }
}

  2. You get back the new quote, with its freshly calculated premium and a generated id, in one round trip. For these inputs the premium works out to 2400, and the id is a fresh UUID (yours will differ).

    Figure 2. Write and read back in one call: the mutation returns the fields you asked for, including the calculated premium

  3. Confirm it was saved by re-running the quotes query you ran earlier; your new home quote is at the end of the list.

Why this matters: A mutation both changes data and returns exactly the fields you ask for, in a single request. In REST that often takes a POST followed by another GET. This "write and read back in one call" is a pattern leaders should recognize when teams weigh REST against GraphQL.

1.11. Compare

Take a moment to compare what you saw:

  • REST: simple, cache-friendly, one URL per resource, but fixed response shapes and sometimes many round trips.

  • GraphQL: one endpoint, client-chosen fields, great for varied clients, but more moving parts on the server and its own caching and security considerations.

Why this matters: Neither is "better." Knowing the trade-off lets you ask the right question when an engineer proposes one: "what problem are we solving: over-fetching, too many round-trips, or just consistency?"

1.12. Review

In this lab you:

  • Called the same data over REST and saw fixed, full-shape responses (over-fetching).

  • Ran GraphQL queries that returned exactly the fields you requested.

  • Used the typed, self-documenting schema through the GraphiQL explorer.

  • Implemented and ran a mutation that writes data and returns chosen fields in one call.

  • Articulated the REST vs GraphQL trade-off at a leadership level.

You explored the two dominant API styles on the Evergreen data, and you can now reason about when each one earns its place. Next week, the quote data behind this API moves out of memory and into MongoDB.
